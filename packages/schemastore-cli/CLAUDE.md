# @effected/schemastore-cli

The `schemastore` command: the companion to `@effected/schemastore`. It loads a `schemastore.config.ts`, builds or checks every declared schema and catalog entry under a per-schema `published` flag and a drift policy, and reports to a terminal, JSON or a GitHub step summary. It is also the home of `AjvValidator`, the one shipped `SchemaValidator` engine — exported so a program driving the library's `SchemaPipeline` itself can run the same engine the command does.

**Design doc:** `@./okf/modules/schemastore-cli.md` — the config contract, the drift table, the command and exit-code contracts, and the reporting shapes. Read it before touching any of them.

## A companion package — one export, no tier

- Companion, not library: tier measures what an importer pays, and the command is the canonical use of this package (the `pnpm-plugin-effect` precedent; see `okf/glossary/companion-package.md`). It runs under a CLI environment and touches the filesystem, which would make a library integrated, but the one thing an importer reaches is a layer over the library's own contract, not a surface of its own.
- Its published surface is the `schemastore` executable, `./package.json` and **exactly one `.` export** (`src/index.ts`), which re-exports `AjvValidator` and nothing else. The export exists so nothing is hidden: a program that drives `SchemaPipeline` itself composes `AjvValidator.layer` and gets the command's verdict. **Never add a second entry or a second export** — every type a config needs (`defineConfig`, `SchemaTarget`, the versioning helpers, the `SchemaValidator` contract) comes from `@effected/schemastore`, and anything that would belong on a library surface belongs there.
- `ajv` and `ajv-formats` are **this package's** dependencies, deliberately not the library's: the engine lives here so an application that imports `@effected/schemastore` at runtime (for `HostedSchema`) never installs or bundles a validator — `okf/decisions/schemastore-engine-lives-in-the-cli.md`. Never move them back.
- `savvy.build.ts` emits declarations for the one entry like any other kit package, with `meta.localPaths: ["../../website/lib/models/schemastore-cli"]` so an api-extractor model lands under `website/lib/models/schemastore-cli/`. The command's documentation is still `--help`, the README and the library's page.
- It runs under `Command.Environment` (`NodeServices.layer` from `@effect/platform-node`), loads consumer TypeScript through `jiti`, and touches the real filesystem.

## The peer rule and why

`effect` and `@effected/schemastore` are **peerDependencies**, never dependencies. The consumer's config constructs `SchemaTarget` values and annotates schemas with symbols that the CLI's pipeline pattern-matches and `Schema.toJsonSchemaDocument` reads; a bundled second copy of either package would fail in ways no type-check catches. One `effect`, one `@effected/schemastore` instance — always.

## Release

A changesets **fixed** group holds `@effected/schemastore` and `@effected/schemastore-cli` at one version, and the CLI's peer range on the library is that exact version (`workspace:*` in source). The package `version` therefore always equals the library's.

## Modules (`src/`)

- `index.ts` — the one library entry: `export { AjvValidator }` and nothing else.
- `AjvValidator` — `AjvValidator.layer: Layer<SchemaValidator>`, the shipped engine (moved from the library's `SchemaValidator.layer` on 2026-09-15, same implementation): ajv strict mode over the Draft-07 meta-schema, every declared `KeywordFamilies` keyword found in the document registered before compiling (through the library's `isDeclared`, so the engine cannot reject what `DocumentLint` allows), `ajv-formats` bound with ONE hop (`ajvFormats.default`) and registered as vocabulary only (`{ keywords: false }` — `formatMaximum` & co. must stay unknown keywords), a fresh `Ajv` per call so shared `$id`s never collide, findings as `ValidationFinding` values (meta-schema failures keep `instancePath`/`keyword`; a compile-time throw becomes a root-pathed finding), and only a mechanism failure on the error channel (`SchemaValidatorError`). The engine suite is `__test__/ajv-validator.test.ts`; the format-registration pins (standard vocabulary compiles, unknown format is a finding, limit keywords still rejected) live there.
- `bin.ts` → `main.ts` — the process boundary and nothing else: the ONLY reads of `process.argv`/`cwd()`/`env`, then `NodeServices.layer`, `CliRuntime.reportFailures` (`3` fallback, renders `error.message`, `[]` for `ShowHelp`) and `NodeRuntime.runMain`.
- `cli/program.ts` — `program(args, deps)`: `Command.runWith` over the tree plus the exit-code mapping (`ShowHelp` → `64` with parse errors / `0` without; `ConfigNotFoundError`/`ConfigLoadError` → `2`, a load error's stack trimmed to its first line and the rest logged at debug) and `loggerLayer` (`CliLogger` with `stderrFrom: "All"` — stdout is `Console.log` only, every log level is stderr). Tests drive this over a test `Command.Environment`.
- `cli/root.ts` and `cli/commands/` — `makeCommands(deps)`: the command tree (`build`, `check`) closed over `ExecuteDeps` (`cwd`, optional `importModule` and `validator` test seams). Environment variables are never injected: they are read through `Config` against the ambient `ConfigProvider` (a `Context.Reference` defaulting to `fromEnv()`), and tests swap it with `ConfigProvider.layer(ConfigProvider.fromEnv({ env }))`.
- `cli/flags.ts` — the shared config argument and `--drift`/`--on-drift`/`--force`/`--format` flags. `--force` is sugar for `--drift=allow` and nothing else: combined with an explicit non-`allow` `--drift` it is a contradiction, not a precedence question.
- `cli/execute.ts` — the shared body, composing `AjvValidator.layer` for the pipeline's `SchemaValidator` (the `validator` test seam substitutes it): first, before the config loads, `--force` with an explicit `--drift` other than `allow` fails `ConflictingFlagsError` marked exit `64` (a usage error, never a silent resolution to `allow`); then load, merge flags over the config's onDrift and per-schema drift, run (a `FrozenVersionMissingError` or `FrozenVersionIdMismatchError` out of `Runner` maps to exit `1`), emit, step summary, then `GateError`/`DriftError`, and for `check` a `StaleError` when any document would be written, an orphaned catalog file sits at `catalogPath`, or the sibling-shape probe reported orphaned documents (all marked exit `1` — `check` is the CI gate, so a stale tree fails it; `StaleError.orphaned` carries the orphan share of `count` so the message names the hand-delete remedy instead of prescribing a build that cannot clear it). `DriftError` carries `drifted: [{ $id, change, version?, nextVersion? }]` — one entry per schema whose verdict is `drift`, `count` derived — and its message lists one line per schema.
- `ConfigLoader` — discovery and `jiti` loading of the config, `defineConfig` validation (exit `2`), plus the shape re-checks a forged brand could skip (`describeMalformed`: a malformed schema target; a `frozen` entry missing `version`/`path`/`$id`/`url`; a duplicate output path after resolving to an absolute path), each guarded ahead of the dereference it protects. Relative `outputDir`, `catalogPath`, each schema's current target `path`, and every frozen predecessor's `path` resolve against the config file's directory.
- `Runner` — the shared build/check walk over `SchemaPipeline`, drift table applied. Before anything is generated, every schema's `frozen` versions are walked: a missing file fails typed `FrozenVersionMissingError` (reported first), and a file that exists is READ and must declare the `$id` its `FrozenVersion` derives — a different `$id`, none, or unparseable text fails typed `FrozenVersionIdMismatchError` (`mismatched: [{ name, version, path, expected, actual?, reason: "mismatch" | "absent" | "unparseable" }]`). Both exit `1` before anything is written: a `baseUrl` change is a re-publish event for every frozen label, and the frozen file is the one document the derivation does not own. A catalog entry is compared with ONE `readFileString` (`NotFound` → absent, unparseable → different) and the library's `CanonicalJson.equals`; no `exists` pre-check and no local `deepEqual`. Every schema's declared catalog entry lands in ONE file at `config.catalogPath`, never one file per schema. When no schema declares a catalog but a file exists at `catalogPath`, `CatalogReport` is `{ path, entries: 0, outcome: "orphaned" }` — stale (exit `1`) under `check`, reported but NEVER deleted under `build` (the CLI may not have written it); the report omits `catalog` only when there is no such file either. Both modes also probe the sibling shapes of every derived path — `SchemaVersioning.fileName` has exactly four per name and label (`<name>.json`, `<name>-<v>.json`, `<v>/<name>.json`, `<v>/<name>-<v>.json`) — for every label the config still declares, and report each FILE that exists and that no target, frozen version, or `catalogPath` claims in `RunReport.orphaned`: the document an `appendVersion` flip or a `layout` change left behind under its old name; stale (exit `1`) under `check`, reported but NEVER deleted under `build`. Nothing else on disk is read — NEVER list `outputDir` (it may be shared with another config, a deploy folder, or the repository root); a `name` change or a dropped label is not caught (the old name is unknowable); a directory wearing a derived name is not a document.
- `Report` — human and JSON renderers; an orphan renders `orphaned catalog <path> (no schema declares a catalog)`, an orphaned document renders `orphaned document <path> (no target, frozen version, or catalog entry claims it — delete it by hand; build never will)`; JSON carries `orphaned` only when present, the step summary gains an orphaned-document table. The human summary's `drift` count is verdict-based: under `onDrift: warn` a drifting schema is written AND counted as drift, so the four counts need not sum to the schema total.
- `StepSummary` — the `GITHUB_STEP_SUMMARY` append (`Config.String(...).pipe(Config.option)`; an empty value is absent), logged-not-fatal.

## Testing and building

- `pnpm build --filter @effected/schemastore-cli`; never run `savvy.build.ts` directly. Confirm `dist/dev/issues.json` `generatedAt` postdates your edit.
- Prove the bin: `node dist/dev/pkg/bin/schemastore.js --help` exits `0`; `--bogus` exits `64`.
- Tests live in `__test__/`, drive `Command.run` in-process over `@effected/memfs`, and assert with `assert.*`. Run them from the repo root with `vitest run --project @effected/schemastore-cli`.
