# @effected/schemastore-cli

The `schemastore` command: the companion to `@effected/schemastore`. It loads a `schemastore.config.ts`, builds or checks every declared schema and catalog entry under a per-schema `published` flag and a drift policy, validates a payload against a published document, and reports to a terminal, JSON or a GitHub step summary. It is also the home of the kit's two shipped engines — `AjvValidator` (the one `SchemaValidator` implementation) and `AjvInstanceValidator` (the one `InstanceValidator` implementation) — exported so a program driving the library's `SchemaPipeline` or validating payloads itself can run the same engines the command does.

**Design doc:** `@./okf/modules/schemastore-cli.md` — the config contract, the drift table, the command and exit-code contracts, and the reporting shapes. Read it before touching any of them.

## A companion package — engine layers only, no tier

- Companion, not library: tier measures what an importer pays, and the command is the canonical use of this package (the `pnpm-plugin-effect` precedent; see `okf/glossary/companion-package.md`). It runs under a CLI environment and touches the filesystem, which would make a library integrated, but the one thing an importer reaches is an engine layer over the library's own contract, not a surface of its own.
- Its published surface is the `schemastore` executable, `./package.json` and **exactly one `.` export** (`src/index.ts`), which re-exports **only engine layers over library contracts**: `AjvValidator` (a `SchemaValidator`) and `AjvInstanceValidator` (an `InstanceValidator`) and nothing else. The exports exist so nothing is hidden: a program that drives `SchemaPipeline` itself composes `AjvValidator.layer`, a program that validates payloads itself composes `AjvInstanceValidator.layer`, and each gets the command's verdict. **Never add a second entry, and never add an export that is not an engine layer over a `@effected/schemastore` contract** — every type a config needs (`defineConfig`, `SchemaTarget`, the versioning helpers, the `SchemaValidator` and `InstanceValidator` contracts) comes from `@effected/schemastore`, and anything that would belong on a library surface belongs there.
- `ajv` and `ajv-formats` are **this package's** dependencies, deliberately not the library's: the engine lives here so an application that imports `@effected/schemastore` at runtime (for `HostedSchema`) never installs or bundles a validator — `okf/decisions/schemastore-engine-lives-in-the-cli.md`. Never move them back.
- `savvy.build.ts` emits declarations for the one entry like any other kit package, with `meta.localPaths: ["../../website/lib/models/schemastore-cli"]` so an api-extractor model lands under `website/lib/models/schemastore-cli/`. The command's documentation is still `--help`, the README and the library's page.
- It runs under `Command.Environment` (`NodeServices.layer` from `@effect/platform-node`), loads consumer TypeScript through `jiti`, and touches the real filesystem.

## The peer rule and why

`effect` and `@effected/schemastore` are **peerDependencies**, never dependencies. The consumer's config constructs `SchemaTarget` values and annotates schemas with symbols that the CLI's pipeline pattern-matches and `Schema.toJsonSchemaDocument` reads; a bundled second copy of either package would fail in ways no type-check catches. One `effect`, one `@effected/schemastore` instance — always.

## Release

A changesets **fixed** group holds `@effected/schemastore` and `@effected/schemastore-cli` at one version, and the CLI's peer range on the library is that exact version (`workspace:*` in source). The package `version` therefore always equals the library's.

## Modules (`src/`)

- `index.ts` — the one library entry: `export { AjvValidator }` and `export { AjvInstanceValidator }`, engine layers over the library's contracts and nothing else.
- `internal/ajv.ts` — `makeAjv(document, strict)`: the ONE ajv setup both shipped engines share — a fresh strict-mode `Ajv` with `allErrors`, `ajv-formats` bound with ONE hop (`ajvFormats.default`) and registered as vocabulary only (`{ keywords: false }` — `formatMaximum` & co. must stay unknown keywords), and every declared `KeywordFamilies` keyword found in the document registered before compiling (through the library's `isDeclared`, so the engine cannot reject what `DocumentLint` allows; the walk stops at a declared key and mirrors the library's `MAX_NESTING_DEPTH`). THROWS when ajv itself refuses the setup; each caller re-marks that throw for its own subject.
- `AjvValidator` — `AjvValidator.layer: Layer<SchemaValidator>`, the shipped document engine (moved from the library's `SchemaValidator.layer` on 2026-09-15): `makeAjv` over the Draft-07 meta-schema, findings as `ValidationFinding` values (meta-schema failures keep `instancePath`/`keyword`; a compile-time throw becomes a root-pathed finding), and only a mechanism failure on the error channel (`SchemaValidatorError`). The engine suite is `__test__/ajv-validator.test.ts`; the format-registration pins (standard vocabulary compiles, unknown format is a finding, limit keywords still rejected) live there.
- `AjvInstanceValidator` — `AjvInstanceValidator.layer: Layer<InstanceValidator>`, the shipped payload engine: the same `makeAjv` pointed at an instance instead of the meta-schema. An instance the document rejects answers `InstanceFinding` values (ajv's `instancePath` preserved as the pointer into the INSTANCE, `allErrors` reports every problem); a document the engine cannot compile fails `InstanceValidatorError` — unlike `AjvValidator`, whose subject IS the document, here the subject is the instance and a document yielding no verdict is a mechanism failure. `strict` defaults to `true`. The engine suite is `__test__/ajv-instance-validator.test.ts`.
- `bin.ts` → `main.ts` — the process boundary and nothing else: the ONLY reads of `process.argv`/`cwd()`/`env`, then `NodeServices.layer`, `CliRuntime.reportFailures` (`3` fallback, renders `error.message`, `[]` for `ShowHelp`) and `NodeRuntime.runMain`.
- `cli/program.ts` — `program(args, deps)`: `Command.runWith` over the tree plus the exit-code mapping (`ShowHelp` → `64` with parse errors / `0` without; `ConfigNotFoundError`/`ConfigLoadError` → `2`, a load error's stack trimmed to its first line and the rest logged at debug) and `loggerLayer` (`CliLogger` with `stderrFrom: "All"` — stdout is `Console.log` only, every log level is stderr). Tests drive this over a test `Command.Environment`.
- `cli/root.ts` and `cli/commands/` — `makeCommands(deps)`: the command tree (`build`, `check`, `validate`) closed over `ExecuteDeps` (`cwd`, optional `importModule`, `validator` and `instanceValidator` test seams). Environment variables are never injected: they are read through `Config` against the ambient `ConfigProvider` (a `Context.Reference` defaulting to `fromEnv()`), and tests swap it with `ConfigProvider.layer(ConfigProvider.fromEnv({ env }))`.
- `cli/flags.ts` — the shared config argument and `--drift`/`--on-drift`/`--force`/`--format` flags. `--force` is sugar for `--drift=allow` and nothing else: combined with an explicit non-`allow` `--drift` it is a contradiction, not a precedence question.
- `cli/execute.ts` — the shared body, composing `AjvValidator.layer` for the pipeline's `SchemaValidator` (the `validator` test seam substitutes it): first, before the config loads, `--force` with an explicit `--drift` other than `allow` fails `ConflictingFlagsError` marked exit `64` (a usage error, never a silent resolution to `allow`); then load, merge flags over the config's onDrift and per-schema drift, run (a `FrozenVersionMissingError` or `FrozenVersionIdMismatchError` out of `Runner` maps to exit `1`, a `CatalogDirError` to exit `2`), emit, step summary, then `GateError`/`DriftError`, then `CatalogMergeError` (both modes, exit `1`) when the merged catalog is `blocked` by a URL or name conflict or an invalid slice (`conflicts` is the tagged union `{ kind: "url", url, slices } | { kind: "name", name, slices }`; the message names `url X` / `name X is advertised by …`), and for `check` a `StaleError` when any document (a catalog slice or the merged catalog included) would be written, the config's slice or the merged catalog is orphaned, or the sibling-shape probe reported orphaned documents (all marked exit `1` — `check` is the CI gate, so a stale tree fails it; `StaleError.orphaned` carries the orphan share of `count` so the message names the hand-delete remedy instead of prescribing a build that cannot clear it). `DriftError` carries `drifted: [{ $id, change, version?, nextVersion? }]` — one entry per schema whose verdict is `drift`, `count` derived — and its message lists one line per schema.
- `cli/commands/validate.ts` — `schemastore validate <payload> [--schema <path|$id>]`: reads the payload (`PayloadError`, exit `2`), resolves the reference file-first then against every identity a config schema derives (`$id`, frozen `$id`/`url`, catalog `url`; `SchemaResolutionError`, exit `2`; no reference at all is `MissingSchemaRefError`, exit `64`), validates with `deps.instanceValidator` or `AjvInstanceValidator.layer`, and fails `ValidationFailedError` at exit `1` with pointer-and-keyword findings; an engine mechanism failure flows unmarked to the runtime's exit `3`. The payload's `$schema` pointer is stripped only when the resolved document does not declare `$schema` as a root property; a document that does (the HostedSchema pattern) validates the payload verbatim. `--format json` writes one report document to stdout and moves the human lines to stderr, exactly as `build`/`check` do.
- `ConfigLoader` — discovery and `jiti` loading of the config, `defineConfig` validation (exit `2`), plus the shape re-checks a forged brand could skip (`describeMalformed`: a `name` that is not a simple file base name; a non-string `outputDir`/`catalogDir`; a malformed schema target; a `frozen` entry missing `version`/`path`/`$id`/`url`; then, on resolved paths, `describeClashingPath`: a `catalogDir` equal to the merged catalog's path (would die EISDIR) or to `outputDir`, a document directly in `catalogDir`, or a duplicate output path — the slice and merged catalog included), each guarded ahead of the dereference it protects. `ConfigLoader.slicePath` (`<catalogDir>/<name>.json`) and `ConfigLoader.mergedCatalogPath` (`catalog.json` in `catalogDir`'s parent) are the one derivation of the two catalog paths, shared with `Runner`. Relative `outputDir`, `catalogDir`, each schema's current target `path`, and every frozen predecessor's `path` resolve against the config file's directory.
- `Runner` — the shared build/check walk over `SchemaPipeline`, drift table applied. Before anything is generated, every schema's `frozen` versions are walked: a missing file fails typed `FrozenVersionMissingError` (reported first), and a file that exists is READ and must declare the `$id` its `FrozenVersion` derives — a different `$id`, none, or unparseable text fails typed `FrozenVersionIdMismatchError` (`mismatched: [{ name, version, path, expected, actual?, reason: "mismatch" | "absent" | "unparseable" }]`). Both exit `1` before anything is written: a `baseUrl` change is a re-publish event for every frozen label, and the frozen file is the one document the derivation does not own. A catalog entry is compared with ONE `readFileString` (`NotFound` → absent, unparseable → different) and the library's `CanonicalJson.equals`; no `exists` pre-check and no local `deepEqual`. Every schema's declared catalog entry lands in ONE slice, `<catalogDir>/<name>.json`, rewritten wholesale — never one file per schema; with none declared, a slice still on disk is `orphaned` (stale under `check`, NEVER deleted under `build`) and still merged. The merged `catalog.json` in `catalogDir`'s parent is the union of every `*.json` file directly in `catalogDir` with the running config's own slice REPLACED by its freshly computed entries ONLY when those are non-empty (then never read from disk, so `check` compares against what a build would produce); with no entries its on-disk orphan is merged as-is, as every other config sees it. The merge is a pure function of disk plus non-empty fresh entries — substituting an EMPTY fresh slice made the merged file ping-pong between configs (round-6 dogfood), sorted by `url` in code-unit order; a `url` two slices advertise or a `name` two advertised entries share (`conflicts`, `kind: "url"` then `kind: "name"`, each sorted by value in code-unit order — a name is counted only over entries the merge advertises, so an entry that lost its URL is reported once, as the URL; one slice advertising a name twice is listed twice) or a slice that cannot be used (`invalid: [{ path, reason }]` — `unreadable: …`, `not JSON`, or the decode's own issues flattened to `<message> at <path>` clauses joined by semicolons, e.g. `Expected no excess property at [0]["extra"]`) makes it `blocked` and unwritten; no slice left with the merged file on disk makes it `orphaned`. `catalogDir` is the ONE directory the Runner lists, and it is listed right after the frozen checks, before anything is generated: `NotFound` → no slices; any other failure (a file → `BadResource`, `PermissionDenied`) → typed `CatalogDirError`, mapped to exit `2` in `execute` (a config problem). Own slice on disk = an EXACT `<name>.json` match; only with none, and exactly ONE listed file case-folding to it, does the Runner PROBE THE VOLUME — `fs.stat(<catalogDir>/<name>.json)` — and claim that file only when the stat succeeds (the volume resolved the exact name to the folded file: case-insensitive). `NotFound` (or any failure) claims nothing: on a case-sensitive volume the variant is another slice, so a case-only rename leftover blocks on the FIRST build like any rename leftover, and `docs`/`Docs` are two slices every config merges alike. Never decide by name alone: a name-only fold claimed a leftover on build 1 and blocked on build 2 (non-idempotent), and let `Docs` hide the real `docs` config's slice. Tests simulate the case-insensitive volume with memfs fault handlers routing `stat`/`readFileString`/`writeFileString` on `Docs.json` to the base volume's `docs.json`. A fold claim is reported on `CatalogSliceReport.caseFoldedMatch` (the on-disk path claimed) and rendered on the slice line as `(N entries; claimed <p> by case-folded match for "<name>")`, in JSON, and in the step-summary outcome cell: on a case-insensitive volume `docs`/`Docs` share one file and overwrite each other, undetectable in general (no owner in a bare-array slice), so names sharing a `catalogDir` must be unique case-insensitively — a documented rule. `CatalogDirError.reason` is human text (`not a directory`, `permission denied`, else the platform description or tag). Other slices are read defensively: vanished between listing and reading (`NotFound`, not a symlink) → skipped; unreadable (dangling symlink via `readLink`, `PermissionDenied`, …) → `invalid`; decoded with `onExcessProperty: "error"` so an undeclared key → `invalid`, never silently stripped. Sibling `catalogDir`s merging into one `catalog.json` are undetectable per config — documented as a rule (share one `catalogDir`), not checked. `RunReport.catalog` is `{ slice?, merged? }`, omitted when both are absent. Both modes also probe the sibling shapes of every derived path — `SchemaVersioning.fileName` has exactly four per name and label (`<name>.json`, `<name>-<v>.json`, `<v>/<name>.json`, `<v>/<name>-<v>.json`) — for every label the config still declares, and report each FILE that exists and that no target, frozen version, catalog slice, or merged catalog claims in `RunReport.orphaned`: the document an `appendVersion` flip or a `layout` change left behind under its old name; stale (exit `1`) under `check`, reported but NEVER deleted under `build`. Nothing else on disk is read — NEVER list `outputDir` (it may be shared with another config, a deploy folder, or the repository root); a `name` change or a dropped label is not caught (the old name is unknowable); a directory wearing a derived name is not a document.
- `Report` — human and JSON renderers; a slice renders `<outcome> catalog slice <path> (N entries)`, the merged file `<outcome> catalog <path> (N entries from K slice(s))`, a blocked merge `CATALOG BLOCKED <path>` plus one indented line per conflict (`url <u> advertised by …` / `name <n> advertised by …`) and per invalid slice (`slice <p> is invalid: <reason>`), an orphaned slice `orphaned catalog slice <path> (no schema declares a catalog; the merged catalog keeps advertising its entries until it is deleted — delete it by hand; build never will)`, an orphaned merged file `orphaned catalog <path> (no catalog slice remains — …)`, an orphaned document renders `orphaned document <path> (no target, frozen version, or catalog entry claims it — delete it by hand; build never will)`; JSON carries `orphaned` only when present and `catalog.merged.conflicts` (each with `kind` plus `url` or `name`, and `slices`)/`invalid` only when non-empty; the step summary gains a catalog table (slice and merged rows, plus a problem table for a blocked merge) and an orphaned-document table; every table cell escapes `\` first, then `|`, and folds line breaks to a space, since cells carry untrusted text (a slice's key names, paths). The human summary's `drift` count is verdict-based: under `onDrift: warn` a drifting schema is written AND counted as drift, so the four counts need not sum to the schema total.
- `StepSummary` — the `GITHUB_STEP_SUMMARY` append (`Config.String(...).pipe(Config.option)`; an empty value is absent), logged-not-fatal.

## Testing and building

- `pnpm build --filter @effected/schemastore-cli`; never run `savvy.build.ts` directly. Confirm `dist/dev/issues.json` `generatedAt` postdates your edit.
- Prove the bin: `node dist/dev/pkg/bin/schemastore.js --help` exits `0`; `--bogus` exits `64`.
- Tests live in `__test__/`, drive `Command.run` in-process over `@effected/memfs`, and assert with `assert.*`. Run them from the repo root with `vitest run --project @effected/schemastore-cli`.
