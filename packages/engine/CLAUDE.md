# @effected/engine

The `effected` tool's shared logic, consumed by its CLI and MCP front ends. The first release reports identity only: `Identity.report` returns an `IdentityReport` (`tool`, the front end's `version`, the carrier `distribution`, and the resolved `effect` version).

`@effected/kit` is a regular dependency (it supplies `Distribution`); `effect` is a regular dependency, because a tool declares its full stack. The `effect` version comes from a JSON import of `effect/package.json`, which stays an external import in the built output.

The `./schema` subpath is the `effected schema` machinery the front ends share. `SchemaRun.run` is the shared body of `build` and `check`: it loads the config, checks its version (`VersionCheck`), runs `Runner`, and answers with a `RunReport` and a verdict, which a front end maps to an exit code or returns as data. It never appends the step summary, which is the CLI's: a read-only MCP call must not write it. `RunReport` and its neighbours are `Schema` classes in `RunReport.ts`: the MCP result is their plain encoding, and `RunReport.Json` is the `--format=json` document, which `Report.json` prints. `ConfigLoader` evaluates a `schemastore.config.*` and the TypeScript and `.json` it imports afresh on every call, because a long-lived server must see an edit. A `type: module` or CommonJS package stays a native import, so reloading keeps one `@effected/schemastore`; an untyped package of ESM `.js` gets a new instance per reload. An imported `.mjs`, `.cjs` or `.js` under `type: module` stays cached by Node's ESM loader, and a sibling workspace package resolved to built `.js` under `type: module` is the same case: an edit to one is not seen until the process restarts, so restart the server. `jiti` has a tilde range because this rests on its routing. The root entry never reaches `./schema`, so reading identity pulls in neither `jiti` nor `ajv`. `@effected/schemastore` is a `workspace:*` dependency, and `ajv` and `ajv-formats` are exact versions, because each decides what the tool outputs.

The `./build` subpath is the `effected build` machinery. `BuildRun.run` checks for a `package.json`, finds the workspace root, loads the config and plugins, runs `Bundler.build`, reads `dist/prod/issues.json` back, appends to the root journals, and answers with `BuildRunResult`. A build that crashes or records an error is a `failed` verdict rather than a failure, so a front end can always render it and the journals always get an envelope. The error channel holds a run that could not start or record, and that includes `ConfigValidationError`, which the bundler raises before any build work. After a crash a `buildOk: true` artifact is a previous build's, because the bundler swallows a failed artifact write, so the answer is rebuilt from the error's report instead. `PassDone` progress is read from the report after the bundler returns, not live. The journals are provided only around the record, so a build holds no watcher. The root entry never reaches `./build`, so reading identity pulls in no build tooling. `@effected/bundler` is a `workspace:*` dependency, because it decides what the tool outputs.

`ActionRun.run` is `./build`'s other body: it checks for a `package.json`, loads the config, fails `NotAnActionError` when there is no `[action]` table, and runs `ActionBuilder.build`. `ValidationFailed` and `BuildFailed` become the verdict `failed` with what happened so far, and every other builder error stays a failure of `run`. It appends to no journal, because the journals record package builds only. The classes a front end needs (`ActionBuildResult`, `BuildResult`, `ValidationResult`) are re-exported here, so the CLI keeps no bundler dependency.

One module per concept; `src/index.ts`, `src/schema/index.ts` and `src/build/index.ts` are the only re-exporting modules. Tests live in `__test__/`.
