# Peer-check oracle fixtures

Each directory holds a `pnpm-lock.yaml` and the verdict `pnpm peers check --json`
gave for the workspace that produced it. The JSON is pnpm's output **verbatim** —
that is the point of an oracle, so do not reformat or hand-edit it.

Generated with **pnpm 11.22.0** on 2026-08-20, via `pnpm install --lockfile-only`
(no `node_modules` needed) with `autoInstallPeers: false` so peers are not
silently installed out from under the case being tested.

The check is run at *fixture-generation* time, never at test time: this package
forbids new local subprocess seams, and a test that needs a live pnpm on PATH is
neither hermetic nor reproducible in CI.

## What oracle agreement does and does not establish

Every fixture here is generated by running a package manager over a workspace
built for this suite. That means **none of them has config-dependency hooks** —
no `.pnpmfile.cjs`, no `configDependencies`, nothing that can rewrite a manifest
during resolution.

So agreement with `pnpm peers check` validates the computation **on workspaces
without config-dependency hooks**, and is **silent about workspaces with them**.
That is the honest boundary of the evidence, and it is worth stating because
agreement across four cases and two workspaces reads like broader coverage than
it is. A disagreement has already been observed on a workspace that does use
them; what these fixtures can say is only that it is not reproduced here.

Widening the claim needs a fixture whose generation includes hook replay, which
is not what any file in this directory is.

## `mixed/`

Four importers, one per case, with `resolvePeersFromWorkspaceRoot` at its default:

- `packages/ok` — react@18.3.1 + react-dom@18.3.1: **satisfied**.
- `packages/unmet` — react@17.0.2 + react-dom@18.3.1: **unmet required** peer.
- `packages/optional` — react-redux@9.2.0 + redux@4.2.1 against its optional
  `redux: ^5.0.0`: **unmet optional** peer.
- `packages/missing` — react-dom@18.3.1 with no react of its own. It is **clean**,
  and deliberately kept as a case: pnpm resolves peers from the workspace root, so
  a sibling importer's react@18.3.1 satisfies it. A checker that reasoned per
  importer manifest rather than per resolved instance would report a false
  positive here.

## `missing/`

One importer depending on react-dom and react-redux with **no react anywhere in
the workspace**, which is what it takes to get a genuinely unresolvable peer.
pnpm reports three `missing` entries for `react`, one of them **transitive**
(`react-redux` → `use-sync-external-store` → `react`) with a two-element
`parents` chain — the case that makes `parents` a path rather than a single
package.

## `npm/` and `bun/`

The same workspace shape written by **npm 11.19.0** and **bun 1.3.14**: an app
pinning react@17.0.2 against react-dom@18.3.1, plus a workspace library declaring
one required and two optional peers. No oracle accompanies them — npm has no
peer-check command that reports a wanted range, and bun has none at all (its only
signal is a stderr line on the install that *changes* the tree, so a check step
running after install sees nothing). That asymmetry is precisely why this
computation reads the lockfile graph instead of shelling out.

They exist to prove the computation is **format-free**: the same code answers for
all three managers with no per-format branch.

## `rootimporter/`

A workspace whose **root importer has real dependencies**, generated with the
same pnpm 11.22.0 recipe. Its point is the join the other pnpm fixtures never
reach: both `mixed/` and `missing/` declare `.: {}`, so the root is answered by
the no-dependencies guard and the join itself is never exercised.

It also carries the ambiguity that makes the join non-trivial. `react-dom@18.3.1`
resolves twice — against `react@17.0.2` for the root and `react@18.3.1` for
`packages/other` — so `name@version` alone cannot say which the root took. The
importer entry's peer suffix can, and pnpm's own verdict (an unmet `react` for
`.`, and a clean `packages/other`) is the check that we read it correctly.

## `ambiguous/`

**Hand-authored**, and the only fixture here that is. It is `rootimporter/` with
one edit: the root's `react-dom` entry records `version: 18.3.1` with the peer
suffix removed. pnpm always writes the suffix, so this cannot be generated — but
it is what a hand-edited lockfile, or a writer that stopped recording it, would
look like, and it is the only way to reach the case where the composed identity
matches nothing while two candidates share the name and version.

The required behaviour there is to **skip**, not to guess a variant: attributing
`react-dom@18.3.1(react@17.0.2)`'s unmet peer to an importer that may have
resolved the other variant would be a fabricated finding, which is worse than a
missing one. No oracle accompanies it, since pnpm cannot produce the input.
