# Catalogs and hook replay — @effected/workspaces

Catalog assembly, the release-age gate, `ConfigDependencyHooks` and the importer-version fallback — the reasoning behind the parent's rules.

**Parent:** [@effected/workspaces context](./CLAUDE.md)

## Catalog assembly is PM-aware

`WorkspaceCatalogs` picks its inline reader by **file presence**: `pnpm-workspace.yaml` selects the pnpm blocks; its absence selects bun's root `package.json` `workspaces.catalog` / `workspaces.catalogs`. `CatalogSet.fromLockfile` likewise reads whichever extension (pnpm or bun) the parsed lockfile carries.

Both **live** inline readers hard-fail on a malformed catalog block or a default catalog declared twice (top-level `catalog` *and* `catalogs.default` for pnpm; `workspaces.catalog` *and* `workspaces.catalogs.default` for bun) — a silently-empty catalog is the "every dependency looks newly added" bug. They share one validator (`validatedCatalogBlocks`), so they fail typed on exactly the same conditions rather than one hard-failing and the other normalizing to `{}`. The at-ref readers (`CatalogSet.fromWorkspaceYaml`, `bunInlineCatalogs`) are deliberately **tolerant** of the same shapes. The presence probe distinguishes genuine absence from a probe FAILURE: a non-NotFound `PlatformError` from `fs.exists` fails typed rather than collapsing to "absent" and selecting the wrong reader.

`releaseAgeGate()` returns an `Effect<ReleaseAgeGate, CatalogAssemblyFailure>`: inline release-age keys and hook contributions combine **strictest-wins** in the same single memoized assemble pass as the catalogs. Malformed inline values hard-fail as `CatalogAssemblyError(source: "manifest")`. There is deliberately **no** top-level `Workspaces` convenience.

## A hook-injected catalog resolves through the lockfile importers

A `catalog:` specifier injected by a pnpm config-dependency pnpmfile hook (`"effect": "catalog:effect:peers"`) is recorded in **neither** committed source a snapshot reads: the workspace declares no such catalog, and pnpm does not record a **peer-only** catalog in the lockfile's `catalogs:` block. Both sides of a before/after diff then resolved it to the same raw string, so a genuine beta bump produced no row and no changeset (`type-registry-effect`, Actions run 30130459942).

The fix is `internal/importerVersions.ts`: when the catalog set cannot answer a `catalog:` specifier, fall back to the version that ref's own lockfile importer entry recorded. Three things about it are load-bearing:

- **The fallback is for the no-op layer; a replaying layer now answers on BOTH sides.** Under `layerNoop` (the default) `WorkspaceSnapshots.at(ref)` executes nothing, so the importer fallback is the only way the ref side resolves a hook-only catalog, and both lockfiles are committed, which is why this shape was chosen. Under `layerLive`/`layerSubprocess`, `at(ref)` replays the ref's `configDependencies` at the versions THAT ref declares (see "resolves the declared version" below), so the two sides of a diff resolve through the same mechanism and no bogus `from: "catalog:effect:peers"` → `to: "<version>"` row is manufactured. Never wire a replaying hooks layer to `WorkspaceCatalogs` without wiring the SAME reference to `WorkspaceSnapshots` — the composites hand one layer to both for exactly that reason.
- **The join is by dependency NAME, across every dependency field.** pnpm writes a peer into the importer block only when it is also installed, so a `catalog:effect:peers` peer's concrete version lives on that importer's `devDependencies` row. Joining by field, or by matching the recorded specifier, finds nothing.
- **Importer versions are raw and MUST be normalized.** `@effected/lockfiles` stores `ImporterDependency.version` verbatim, peer suffix included (`4.0.0-beta.101(effect@4.0.0-beta.101)(…)`); unstripped, that whole chain lands in a consumer's dependency table as the version. `link:`/`file:` entries are skipped — a filesystem edge is not a version.

## `ConfigDependencyHooks` — opt-in pnpmfile replay

A pnpm config dependency's pnpmfile `updateConfig` hook can mutate catalogs; replaying it executes config-dependency code, so it is gated behind explicit layers. `layerNoop` returns `{ catalogs: seed, releaseAge: {}, peerDependencyRules: <seeded, or empty> }` untouched; `layerLive` dynamically `import()`s each pnpmfile **in process**; `layerSubprocess` replays it in a `node` child process and therefore requires core's `ChildProcessSpawner` in `R`; `layerFrom(entries)` replays caller-supplied files with no resolution (the test seam). Composite mapping (on both `WorkspaceCatalogs` and `Workspaces`): `layer` → `layerNoop`, `layerWithConfigDependencies` → `layerLive`, `layerWithConfigDependenciesSubprocess` → `layerSubprocess`. In `Workspaces` the hooks layer is built **once per composite** and handed to both `WorkspaceCatalogs` (through `WorkspaceCatalogs.layerWithHooks(hooks, options)`, the one builder every `WorkspaceCatalogs.layer*` static delegates to) and `WorkspaceSnapshots` (`withGit(hooks, options)` builds the core over the same reference itself) without ever appearing in the public `WorkspacesServices` output — one reference, so memoization holds and the two sides of a diff cannot run different policies.

`inject` returns a `HookInjection { catalogs, releaseAge, peerDependencyRules, replays }` — **one replay, four outputs**. `replays` is `name → HookReplay { version, source: "installed" | "store" | "supplied" }` for every dependency the layer RESOLVED (a dependency shipping no pnpmfile is still recorded — it contributed nothing, but the version it was resolved at is evidence); `layerNoop` returns `{}`. `WorkspaceCatalogs.hookReplays()` exposes it off the same memo as `set()` — `{}` on the bun/`package.json` path where config dependencies do not exist, exactly as `importerVersions()` answers there. `source` (the `HookReplaySource` union, defined once in `ConfigDependencyHooks.ts`) is machine-local provenance and stays on this live diagnostic; the serializable `WorkspaceStateSnapshot.hookReplays` carries versions only ([snapshots](./CLAUDE.snapshots.md)). Release-age keys thread last-hook-wins; malformed hook values are tolerantly dropped (`CatalogAssemblyError` stays mechanism-only). A `..` segment in a config-dependency name, a declared version that is installed nowhere, or a hook that fails to load or replay, fails typed as a `hooks`-source `CatalogAssemblyError` — never a silent skip.

### The replaying layers resolve the DECLARED version, never "whatever is installed"

A `configDependencies` value is `<version>+<integrity>` or a bare `<version>` (pnpm 12 writes a bare one in a fresh workspace); the declared version is the text before the first `+`. `node_modules/.pnpm-config/<name>` is a symlink into the pnpm store's `links/` tree, and the store keeps **every** version ever installed on the machine at `<store>/links/<name>/<version>/<hash>/node_modules/<name>/` — so a past ref's pnpmfile is recoverable with no checkout, no fetch and no registry. `src/internal/configDependencyResolution.ts` is that ladder, shared by `layerLive` and `layerSubprocess` (the parent resolves; the subprocess only imports what it is handed):

1. `<root>/node_modules/.pnpm-config/<name>` when its `package.json` `version` equals the declared version — today's behaviour, now guarded.
2. Otherwise the store: located from `<root>/node_modules/.modules.yaml` `storeDir`, then the realpath of any `.pnpm-config` entry walked up to its `links` ancestor, then `$PNPM_HOME/store`, `$XDG_DATA_HOME/pnpm/store` and the platform defaults (each expanded to its `v*` subdirectories). `links/<name>/<declared>/*/node_modules/<name>` is enumerated and the inner manifest's `version` **verified** (`<hash>` is not derivable from the integrity, and the path is not trusted).
3. Otherwise fail closed: the error names the package and declared version, what `.pnpm-config` holds (a version, or "nothing"), the stores searched, and the remediation — `pnpm add --config <name>@<declared>` in a throwaway workspace (measured: `pnpm store add` does NOT populate `links/`).

In the chosen directory the first of `pnpmfile.mjs`, `pnpmfile.cjs`, `pnpmfile.js` present in ONE `readdir` listing is loaded; a listed-but-unreadable file (`EACCES`) is still handed to `import()` and fails typed there, so an existing-but-inaccessible pnpmfile never reads as "ships no hook". None listed → that dependency contributes nothing, the one legitimate skip. Store discovery runs at most once per `resolvePnpmfiles` call, lazily on the first `.pnpm-config` miss, and the dependencies resolve concurrently in declaration order. A dependency directory with no `package.json` is "nothing installed", not a match. Because the file's existence is settled before `import()`, **every** load failure is a real error: the old `err.url`-equality skip discrimination is gone on both layers. The ladder reads through `node:fs`, never the effect `FileSystem` — the store is real even when a test's FileSystem is memfs.

`ConfigDependencyHooks.layerFrom(entries)` is the hermetic seam: `"<name>@<version>"` → absolute pnpmfile path, replayed in process with the same locator, threading and error shapes, and **no resolution** — it consults neither `.pnpm-config`, the store, nor any `FileSystem` service, so it works under a memfs volume. A declared `(name, version)` with no entry fails closed in the same `hooks` shape.

**`peerDependencyRules` is SEEDED, never merged by the kit.** pnpm's suppression policy has two sources — the `pnpm-workspace.yaml` block (`pnpm:export` materializes it here) and config-dependency pnpmfiles (never materialized) — and `inject`'s fourth parameter carries the first *into* the threaded config so the hooks merge onto it, exactly as pnpm seeds its own config and takes back what the hooks return. A kit-owned merge function would be a second implementation of a rule this seam already enforces, and the two would drift the first time pnpm changed. **Measured, and not a bug to repair:** this repo's plugin merges onto the seed; another plugin could overwrite it — under seeding that is pnpm's behaviour reproduced, since a hook that overwrites overwrites for pnpm too. Both are pinned by tests.

Each rules axis threads **independently**, so a malformed `ignoreMissing` cannot blank a well-formed `allowedVersions`. All three axes are applied by `PeerCheck`, each measured against `pnpm peers check` with a firing control ([peers](./CLAUDE.peers.md)): `ignoreMissing` and `allowAny` are `@pnpm/matcher` peer-name patterns (`*` wildcard, leading `!` negation — `internal/peerPatterns.ts`, whose single-pattern primitive is `@effected/npm`'s `ReleaseAgeGate.matchesExclude`), and `allowedVersions` keys appear in **two spellings** that both must be handled: parent-versioned from the workspace file (`"@effect/ai-anthropic@4.0.0-rc.109>effect"`) and unversioned from a plugin (`"@effect/vitest>vitest"`).

The rules reach a consumer through `WorkspaceCatalogs.peerDependencyRules()`, memoized with `set()` off the same single read and replay. That call-site read is **pinned by an integration test** (`ConfigDependencyHooks.int.test.ts`), because computing the rules in `inject` and then dropping them at the call site would compile, pass every seam unit test, and return an empty set indistinguishable from "this workspace declares none" — the discard-by-projection defect the seam itself had. `NoPeerDependencyRules` is exported so "assert none apply" is one token rather than three hand-written empty axes.

## `layerSubprocess` exists because a bundler cannot see through a computed import

`layerLive` computes its `import()` target at runtime, and a bundler (rspack) compiles a computed dynamic import into a context module that throws `Cannot find module 'file:///…'` — so `releaseAgeGate()`, the reason an Action opts into hooks at all, was uncallable from any bundled GitHub Action (#280, a silk-update-action dogfood request). `layerSubprocess` moves the computed load out of the bundle graph. Five things are load-bearing:

- **The replay program is a STATIC string constant and the runtime values travel via argv** — `node --input-type=module -e <script> <seedJSON> <rulesJSON> <entriesJSON>`, read back as `process.argv.slice(1)`; `entriesJSON` is the parent-resolved `[[name, fileUrl], …]` array — the parent converts each pnpmfile path with `pathToFileURL`, so the child imports what it is handed and needs no `node:url`. Interpolating any runtime value into the script text puts it back in front of the bundler and reinstates the bug.
- **Typed-semantics parity with `layerLive` is the contract**, pinned by integration tests driving both layers against one on-disk fixture (`ConfigDependencyHooksSubprocess.int.test.ts`, `ConfigDependencyResolution.int.test.ts`): the same declared-version ladder run in the PARENT, the same `.mjs`/`.cjs`/`.js` candidate order, the same hook-locator shapes, the same synchronous call, the same tolerant threading, the same `"hooks"`-source error attribution, and the same `..`-segment refusal — validated **before** spawning, so no subprocess ever sees a traversal name or performs a lookup. A dependency set that resolves to no pnpmfile spawns nothing. Change one side and change the other.
- **The child's protocol payload is framed by `@effected/commands`' `Run.jsonLine`** against a strict `{ ok: true, config } | { ok: false, name?, message?, stack? }` schema — last non-empty stdout line, parsed regardless of exit code, so a hook's own `console.log` noise is tolerated. The hand-rolled copy of that framing was deleted; do not reintroduce it.
- **The rules seed rides argv, in its own slot** (`seedJson, rulesJson, entriesJson`) — never spliced into the program text, which must stay a static string for the same reason the seed and the resolved paths do.
- **Folding and normalization stay in the PARENT.** The child returns only the raw threaded config slice (it cannot import kit code); `configOf` / `configToEntries` / `releaseAgeOf` run here, on the same `@pnpm/catalogs`-derived path `layerLive` uses.
