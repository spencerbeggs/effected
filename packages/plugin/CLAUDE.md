# @effected/plugin

The effected carrier: no logic of its own. `src/index.ts` re-exports the authoring surface of a `schemastore.config.ts` from `@effected/schemastore`: `defineSchemastore` (its `defineConfig`), `HostedSchema`, `SchemaTarget`, `SchemaVersion`, `SchemaVersioning`, `DriftPolicy`, `KeywordFamilies`, `CatalogEntry`, `SchemastoreVersion` and their types. `src/bin/effected.ts` and `src/bin/effected-mcp.ts` each call their front end's `main` (`@effected/cli/main`, `@effected/mcp/main`) with `distribution: { name: "@effected/plugin", version: PLUGIN_VERSION }`; `src/version.ts` holds `PLUGIN_VERSION`, which the bundler replaces at build.

- The front ends declare the same bin names on purpose (each also installs alone), so the e2e passes `allowSharedBins` and proves the carrier's shims with `runCarrierBin` / `carrierCommand`.
- **The published package carries the tool inside it.** `effected.toml` inlines `@effected/cli`, `@effected/mcp`, `@effected/schemastore` and `effect` (`bundle`, a bare name covering its subpaths) and, through them, every kit package, `@effect/*`, `ajv` and the other pure JS below; the build drops them from the emitted `dependencies`. What stays an import is exactly what the source manifest still declares: the build toolchain (`tsdown`, `rolldown`, `rolldown-plugin-dts`, `@tsdown/exe`, `@microsoft/api-extractor`, `@microsoft/tsdoc`, `@microsoft/tsdoc-config`), `jiti` (it loads its own dist by relative path), Ink and React (cli-kit finds Ink's chalk from Ink's own location), and the peers: `typescript`, `@types/node`, and the optional `effect` (the root's declarations import it), `satori` and `@resvg/resvg-js`. A dependency added to `cli`, `mcp` or the engine is inlined unless this manifest declares it, so a package that must stay external is declared here.
- Each inlined package keeps its own `process.env.__PACKAGE_VERSION__` (the bundler stamps it per package), so `--version`, the MCP server's version and the schemastore stamp the version check reads are the inlined packages' own. The build writes `THIRD_PARTY_LICENSES.txt` for what it inlined, and copies `@effected/bundler`'s Open Graph font into `assets/`. `turbo.json` adds `^build`, because the root's declarations inline schemastore's built ones.
- `__test__/e2e/packed-install.e2e.test.ts` packs the carrier alone from `dist/prod/npm/pkg`: build it first with `pnpm build --filter @effected/plugin...`. It skips locally without that build and fails under CI. Its pnpm workspace case proves the `publicHoistPattern` that `@effected/pnpm-plugin-effected` sets. Its schema consumer installs its own `@effected/schemastore` from the workspace and an `effect` a patch behind the carrier's.
- `__test__/entry.test.ts` holds what the e2e cannot see cheaply. **The root stays cheap**, because a config file imports it: it reaches no front end, no `@effected/engine`, no `@effected/bundler`, no `tsdown`, no `ajv`, no `jiti` and no Ink. The built root runs under a module recorder: it resolves nothing outside its own files, and none of the files it loads holds a marker of those parts, with a control proving every marker is somewhere in the package. A static import from a bin shim's graph into `src/index.ts` costs every config that. It also holds the emitted manifest, the root's one `effect` type import, the licence file, and the built root's schemastore stamp.
- **The chain is pinned with `workspace:*`, a build-time input**: this package inlines what it pins, so the pins decide what the build holds and publish nowhere here. Below the carrier, where `cli`, `mcp` and `engine` still publish as packages of their own, they publish as exact versions. The links: this package to `@effected/cli`, `@effected/mcp` and `@effected/schemastore`; `cli` and `mcp` to `@effected/engine`; `engine` to `@effected/schemastore` and `@effected/bundler`; `bundler` to `@effected/changesets`; `schemastore` to `@effected/semver`. A patch floating in below would change the tool's output with no plugin bump, so bumping `schemastore` ripples down the chain. `entry.test.ts` reads the six manifests. Never loosen a link to `workspace:^`.
- **Every other kit dependency of the tool's packages is `workspace:*` too** (`plugin`, `cli`, `mcp`, `engine`, `bundler`): the tool owns its closure, so a kit patch never floats in under a carrier version (effected#1333). Pinning them here also pins each library's kit peers, which resolve from the tool. For the carrier that is the full seal: a library's own kit dependencies are inlined at the version the workspace holds, and no install, override or catalog round reaches them. `@effected/cli` and `@effected/mcp` installed alone still resolve their libraries' own kit edges by caret. `entry.test.ts` holds all five manifests to it.
- The schema cases in the e2e copy `__test__/e2e/fixtures/schema-consumer` into each installed consumer and compare what `effected schema build` writes with its `expected/`, byte for byte. An `effect` advance that changes the output changes that copy: read the difference first, then run `pnpm exec effected schema build` from the fixture's directory, whose `outputDir` is `expected`. The mismatch case makes its second `@effected/schemastore` by rewriting the real tarball's version and stamp, because a stale copy has nothing to install from.
- **`public/tsconfig/{ecma,root}.json` are the presets a consumer's tsconfig extends**, as `@effected/plugin/tsconfig/*`. They live under `public/` because the build copies only that directory into the package, and the export's `./public/` prefix is stripped from the emitted manifest. A bare `tsconfig/` directory would keep the export and ship no files. `__test__/tsconfig-presets.test.ts` follows a consumer's `extends` through the built package with the compiler.
- **`public/env.d.ts` is the `./env` export**: an ambient, types-only declaration of `process.env.__PACKAGE_VERSION__`, which the bundler copies to `env.d.ts` and exports as `{ types }`. Keep it out of `src/`, which would put it in this package's own program and break `@effected/bundler`'s `process.env` weak-type use. Proven in `__test__/tsconfig-presets.test.ts`.
- **`typescript` and `@types/node` are peers here and on `@effected/cli`, `@effected/mcp` and `@effected/engine`,** so a consumer's install surfaces the bundler's peer. It is not only a courtesy: `@effected/bundler` peers a prerelease `typescript` that `tsdown`'s optional peer range does not admit, and with no peer at the installed package npm's resolver spins at full CPU and never finishes. The packed-install e2e's `@effected/mcp` alone case times out without it.
- `typescript` is peered as the literal `7.1.0-beta || 7.1.1-rc || >=7.1.0 <8`, not `catalog:effected:build:peers`, because that catalog value pins a prerelease exactly and a plain lower bound would admit `-dev` nightlies; the plugin's `entry.test.ts` holds the five manifests (bundler, engine, cli, mcp, plugin) to the same string.
- Nothing belongs here but bin shims and those re-exports. Shared logic goes in `@effected/engine`.
