# Advanced

## Strict input

Core's own `Tool.Strict` annotation already rejects a call carrying an
unknown key, decoded with `onExcessProperty: "error"` — but it reports
only the *first* excess key, so a caller fixes one typo per round trip and
never learns about a nested one until the next call. `@effected/mcp`
offers two ways to close the gap, at different scopes.

### `ToolInputSchema` — pure walkers

For a tool whose input is **raw JSON Schema** — a `Tool.dynamic` tool —
nothing in core strictly validates the payload: core decodes it as
`Schema.Unknown`, and dies at registration if the tool is annotated strict.
Run the walkers inside the handler instead, against the JSON Schema you
registered. The pairing with `objectRooted` is the common case: a
top-level discriminated union only reaches a server as raw JSON Schema,
because core dies at boot on a union root.

```ts
import { McpToolkit, ToolInputSchema } from "@effected/mcp";
import { Effect, Layer, Schema } from "effect";
import { Tool, Toolkit } from "effect/unstable/ai";

// A top-level union, written as raw JSON Schema and rewritten to an object root.
const EditInput = ToolInputSchema.objectRooted({
  anyOf: [
    {
      type: "object",
      properties: {
        action: { const: "rename" },
        to: { type: "string" },
        options: { type: "object", properties: { force: { type: "boolean" } }, additionalProperties: false },
      },
      required: ["action", "to"],
      additionalProperties: false,
    },
    {
      type: "object",
      properties: { action: { const: "delete" } },
      required: ["action"],
      additionalProperties: false,
    },
  ],
});

class UnknownKeys extends Schema.TaggedError<UnknownKeys>()("UnknownKeys", { message: Schema.String }) {}

const Edit = Tool.dynamic("edit", {
  description: "Rename or delete a thing.",
  parameters: EditInput,
  failure: UnknownKeys,
});

const EditTools = Toolkit.make(Edit);

const EditHandlers = EditTools.toLayer({
  // A dynamic tool is decoded as Schema.Unknown: the handler sees the raw payload.
  edit: (payload) => {
    const levels = ToolInputSchema.unknownKeys(payload, EditInput);
    return levels.length > 0
      ? Effect.fail(new UnknownKeys({ message: ToolInputSchema.formatUnknownKeys(levels) }))
      : Effect.succeed(payload);
  },
});

// McpToolkit never re-annotates a Tool.dynamic tool, so it stays lenient and the handler reports.
const EditLayer = McpToolkit.layer(EditTools).pipe(Layer.provide(EditHandlers));
```

`formatUnknownKeys` writes one sentence per object level that carries an
unknown key:

```text
edit({ action: "rename", to: "b", extra: 1, options: { force: true, bogus: 2 } })
=> Unrecognized parameter(s): extra. Accepted params: action, to, options. Unrecognized parameter(s): options.bogus. Accepted params: force.
```

This recipe is for dynamic tools only. For a `Tool.make` tool, core
decodes the payload *before* the handler runs, so an excess key is already
dropped (lenient) or rejected (strict) by the time a handler could look —
use `McpToolkit` there.

`unknownKeys` follows `$ref` (into `$defs`, JSON Pointer escapes
honoured), merges `allOf` properties, chooses a discriminated `oneOf`/
`anyOf` member by an `action`, `kind`, `_tag` or `type` literal, and walks
`items`/`prefixItems` and `patternProperties` — the same schema shape core
serves for a strict tool. Only `additionalProperties: false` closes a
node; a missing value, `true`, or a schema-valued `additionalProperties`
all leave it open.

`objectRooted` inlines a root `$ref` and rewrites a top-level union of
objects sharing an `action`, `kind`, `_tag` or `type` literal to an object
root carrying `oneOf` and `"x-discriminator"` — MCP requires an object
root. It returns the schema unchanged when there is nothing to rewrite.

### `McpToolkit` — strict by default, complete reporting

The registration-scoped decorator is the recommended default for a new
server. It runs core's `registerToolkit` unchanged, under a `McpServer`
whose `addTool` puts an `unknownKeys` pre-check in front of each handler:

```ts
import { McpToolkit } from "@effected/mcp";
import { Layer } from "effect";

// Every tool without its own Tool.Strict annotation is served and decoded
// strict; a rejected call names every unknown key at every depth in one
// InvalidParams, not just the first.
const ToolsLayer = McpToolkit.layer(MyTools).pipe(Layer.provide(MyHandlers));

// Leave unannotated tools lenient; only explicitly-annotated tools are strict.
const LenientByDefault = McpToolkit.layer(MyTools, { strict: "annotated" }).pipe(
  Layer.provide(MyHandlers),
);
```

An explicit `Tool.Strict` annotation — true or false — always wins over
the default in either mode, and a `Tool.dynamic` tool is never
re-annotated: core dies at registration on a strict dynamic tool, because
it cannot strictly validate a raw JSON Schema. Only a tool that ends up
strict gets the pre-check, gated on the same predicate core uses to
choose strict decoding — a lenient tool is never rejected here, even when
its raw schema happens to carry `additionalProperties: false`.

`McpToolkit`'s default `strict` mode is `"all"`: real-traffic evidence
against Claude Code 2.1.281 found every tool call's `arguments` carrying
exactly the tool's declared keys, with every protocol extra confined to
the sibling `params._meta` — so an all-strict default rejects nothing a
real client sends.

### Union-parameter tools

A tool whose parameters are a `Schema.Union` of objects cannot be a
`Tool.make` tool: core dies at registration on a non-object `parameters`
root. `McpToolkit.unionTool` makes it a `Tool.dynamic` served with Effect's
strict JSON Schema for the union, object-rooted with `oneOf` and
`x-discriminator`, and `McpToolkit.unionHandler` hands your handler the
decoded member:

```ts
import { McpToolkit, ToolRefusal } from "@effected/mcp";
import { Effect, Schema } from "effect";
import { Tool, Toolkit } from "effect/unstable/ai";

const Note = McpToolkit.unionTool("note", {
  parameters: Schema.Union([
    Schema.Struct({ action: Schema.Literal("add"), text: Schema.String }),
    Schema.Struct({ action: Schema.Literal("list") }),
  ]),
  success: Schema.Struct({ ok: Schema.Boolean }),
  failure: ToolRefusal,
}).annotate(Tool.Title, "Note");

const Handlers = Toolkit.make(Note).toLayer({
  note: McpToolkit.unionHandler(Note, (params) => Effect.succeed({ ok: params.action === "add" })),
});
```

Under `McpToolkit.layer`, a union tool's unknown keys are all named in one
`InvalidParams` and the union is decoded strictly, both before the handler
runs. So bad arguments answer exactly as a `Tool.make` decode failure does:
`-32602` on `2025-06-18`, `isError` on the later revisions. Under core's
`McpServer.toolkit` the handler still rejects them, but as a declared
failure, an `isError` result on every revision. `annotate` and
`addDependency` keep the union on the tool, so chaining them is safe.

## Crash guards

`@effected/mcp/guard` exports `McpGuard.run`. It installs
`uncaughtException` and `unhandledRejection` listeners before your server
graph loads, and the entrypoint has no static runtime import. It then awaits
your `load()` and launches the server:

```ts
import { McpGuard } from "@effected/mcp/guard";

await McpGuard.run({
  label: "my-server",
  host: process,
  policy: { onUncaught: "exitBeforeConnect", onRejection: "log" },
  load: async () => {
    const NodeRuntime = await import("@effect/platform-node/NodeRuntime");
    const { Main } = await import("./server.js");
    return { layer: Main, runMain: NodeRuntime.runMain };
  },
});
```

| Policy | Before the server is serving | After |
| --- | --- | --- |
| `"exit"` (the default for both) | exit 1 | exit 1 |
| `"exitBeforeConnect"` | exit 1 | log, keep serving |
| `"log"` (rejections only) | log | log |

- "Serving" means the whole layer has built and stdin is being read,
  before any `initialize`. The signal is `McpStdio.launch`'s `onReady`.
- A rejected `load()` is `startup failed` and exit 1 under every policy.
- Registering an `unhandledRejection` listener disables Node's default
  throw, so `"log"` keeps the process alive.
- A guard's exit skips Effect finalizers and the teardown.
- A layer build failure is still reported by `McpStdio.launch`.

`injectCrashAfterConnect` raises an exception or rejection on a timer
right after the server is serving, for a test of the guards themselves.

## Testing

### In-process, with `McpHarness`

The default for testing a server: no child process, no sockets, and the
exact served schemas and wire results a real client would see, over a
queue-backed `Stdio.layerTest`.

```ts
import { McpHarness } from "@effected/mcp/testing";
import { Effect } from "effect";

const test = Effect.gen(function* () {
  const client = yield* McpHarness.make(ServerLayer);
  yield* client.initialize; // initialize + notifications/initialized: every stateful revision requires it
  const result = yield* client.callTool("get_thing", { id: "known" });
  // result.result.structuredContent === { name: "a known thing" }
  yield* client.close;
});
```

Pass `server` **without** a `Stdio` of its own — one it provides
internally wins, and talks to the real terminal instead of the harness's
queues. Every response wait and `awaitOutboundMethod` races a stop signal
and a corruption signal, so a server that stops before responding, or
writes a non-JSON-RPC line under `strictStdout` (default `true`), fails
or dies the wait rather than hanging the test. With `captureLogs` (default
`true`), assert `client.stderrSoFar` and `client.consoleLogSoFar` —
anything on `consoleLogSoFar` in a real server would have corrupted the
wire.

On a stateful revision — the default is `2025-11-25` — `yield*
client.initialize` before anything else. A request sent before an
`initialize` fails fast with `McpTestFailure` reason `NotInitialized`,
naming the revision, instead of reaching a server that would only answer
an opaque `Invalid request metadata`. `sendRaw` is never gated, so a test
can still drive that refusal on purpose. The stateless `2026-07-28`
revision needs no handshake.

`client.initializeWith(protocolVersion)` sends `initialize` asking for a
different stateful revision than the harness was made with, and returns
the whole response. Use it to test version negotiation by asserting the
negotiated `result.protocolVersion`. A stateful server never refuses a
version: an unknown one, or the stateless `2026-07-28`, is counter-offered
`2025-11-25`. On a harness made with the stateless revision, `initialize`
is not served at all: the response is a JSON-RPC `-32601` error, and no
`notifications/initialized` follows it. `client.sentSoFar` lists every
frame the harness has written, in order.

### A spawned bin, with `McpProcess`

For a test that must exercise a **built** bin rather than a layer:

```ts
import { McpProcess } from "@effected/mcp/testing";
import { ChildProcess } from "effect/unstable/process";
import { Effect } from "effect";

const test = Effect.gen(function* () {
  const command = ChildProcess.make(process.execPath, ["./dist/bin.js"], {
    env: { PATH: process.env.PATH ?? "" },
  });
  const child = yield* McpProcess.spawn(command);
  yield* child.handshake();
  yield* child.send({ jsonrpc: "2.0", id: 2, method: "tools/call", params: { name: "get_thing", arguments: { id: "known" } } });
  const { response } = yield* child.readUntilResponse(2);
  yield* child.closeStdin; // Queue.end — every frame already sent is delivered first
});
```

`nextLine` fails with `StreamEnded` at end of stream, so a child that
exits early fails the test instead of hanging it. `closeStdin` is
`Queue.end`, never `Queue.shutdown` — a request in flight when stdin
closes is dropped by an Effect server, so read its response first.

### The packed-install proof, with `McpProbe`

The MCP half of a packed-install proof — the smallest check that an
installed bin actually boots:

```ts
import { McpProbe } from "@effected/mcp/testing";

const result = yield* McpProbe.initialize(command);
// assert result.response.error === undefined, result.stderr === "" and result.exitCode === 0
```

Stdin stays open until the id-1 response arrives, then closes — closing
right after writing, as a hand-rolled smoke test typically does, makes an
Effect server drop the in-flight response and exit `0`, reading as a pass
with no response at all. Assert `result.response.error === undefined` as
well: a server that refuses the handshake still answers id 1, exits `0`
and writes nothing to stderr.

### A pure policy sweep, with `McpToolAudit`

No server needed — feed it a `tools/list` result and read the violations
as data:

```ts
import { McpToolAudit } from "@effected/mcp/testing";

const violations = McpToolAudit.check(tools, {
  input: "closed",
  requireTitle: true,
  // objectRootedOutput defaults to true: the stateless 2026-07-28 adapter
  // passes a non-object tool output through verbatim, while the stateful
  // revisions drop it from the served tool entirely.
});
```

A duplicate tool name is reported under **every** policy, independent of
`input`, `requireTitle`, or any other option — two registered tools
sharing a name is always a violation, never something a permissive
policy exempts:

```ts
import { McpToolAudit } from "@effected/mcp/testing";

McpToolAudit.check(
  [
    { name: "search", inputSchema: { type: "object" } },
    { name: "search", inputSchema: { type: "object" } },
  ],
  { input: "any" }, // even the most permissive policy still catches this
);
// => ["search: duplicate tool name"]
```

Run it against what a real server serves (`McpHarness.listTools`), not
against your own source schemas — the served document is what a client
actually sees, and it can differ by protocol revision.

A union success schema fails `objectRootedOutput`: a top-level
`Schema.Union` emits a bare `anyOf`. Wrap it in
`ToolOutputSchema.objectRooted` (from `@effected/mcp`), which adds
`type: "object"` beside the `anyOf` without changing decoding. It works
before or after `.annotate({ identifier })`.

## `InvalidParams` per protocol revision

A rejected call's shape on the wire differs by revision:

| Revision | Shape |
| --- | --- |
| `2024-11-05` | JSON-RPC error, code `-32602` (core's behaviour; not served by `McpStdio.protocols`) |
| `2025-03-26` | JSON-RPC error, code `-32602` (core's behaviour; not served by `McpStdio.protocols`) |
| `2025-06-18` | JSON-RPC error, code `-32602` |
| `2025-11-25` | `isError: true` tool result |
| `2026-07-28` (stateless) | `isError: true` tool result |

A union tool registered through `McpToolkit.layer` follows the same
table. Registered through core's `McpServer.toolkit`, its rejection is a
declared failure: an `isError` result on every revision.

A test suite covering only one shape misses the other half of the matrix
— `@effected/mcp`'s own tests cross the three revisions `McpStdio.protocols`
serves (`2025-06-18`, `2025-11-25` and `2026-07-28`) with success,
declared failure and invalid params. The two older rows record core's own
adapters, which `@effected/mcp` neither serves by default nor tests.
