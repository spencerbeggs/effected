# effected

A pnpm monorepo (npm org `@effected`) building an [Effect](https://effect.website/) v4 app kit: a set of
libraries designed for Effect v4 from the start, not lifted from their v3 predecessors. The repo holds
libraries only — the applications that consume them stay in their own repos.

Scope is closed by five consuming applications, not by how many source repos remain. A library earns its
place by being something one of those five actually needs.

## How this ships

Every package below is on npm, including [@effected/pnpm-plugin-effect](/pnpm-plugin-effect) — it is not a
library, so the tier taxonomy does not describe it, but it is a public package and it publishes like the
rest. Everything is `0.x` and unstable; `1.0.0` waits for Effect v4 GA.

Releases are changeset-driven. CI releases whatever the pending changesets name, which is sometimes the
whole kit and sometimes one package on its own — both are ordinary, and versions move per package rather
than in lockstep. Each package's npm page is the source of truth for the version to install.

What is coordinated is the Effect pin: every package is built against the single beta named in the `effect`
catalog, so peer ranges agree with each other, and advancing that beta is a change across the whole kit
rather than a per-package decision.

The API reference in these pages is generated from the source of the published packages.

## Tiers

Every **library** declares a tier, which describes its runtime surface:

* **pure** — peers on `effect` and takes only `@effected/*` edges, with no IO.
* **boundary** — the same dependency surface, but does IO through Effect's core `FileSystem` and `Path`
  services.
* **integrated** — imports at least one runtime package outside `effect` core.

The tier is a dependency statement rather than an IO one. A package with no IO at all still vendors its
engine rather than take a runtime dependency, which is why `@effected/glob` is pure despite carrying a
ported matcher. A library's tier tells you what depending on it will cost you.

### Companion packages

A **companion** package is published and installable but is **not a library**: it exposes no API, so there
is nothing to import and nothing to call. Companion is a category, not a fourth tier — the three tiers sit
on one axis, dependency surface, and that axis is meaningless for a package nothing can depend on. A
companion has no tier rather than a fourth one.

[@effected/pnpm-plugin-effect](/pnpm-plugin-effect) is the only companion today. It ships four pnpm catalogs
and a pnpmfile — configuration, not code. Two of them pin Effect; the other two, `catalog:effected` and
`catalog:effected:peers`, name every published package on this page except the companion itself, so a consumer references a catalog
instead of maintaining a version range per package. Installing it is optional for you; publishing it is not
optional for the kit, since it is what holds a consumer's versions where the libraries expect them.

Installing [@effected/pnpm-plugin-effect](/pnpm-plugin-effect) holds your `effect` versions, your
`@effected/*` versions and both sets of peer floors at exactly the values this kit was built and tested
against, rather than leaving you to resolve your own.

## What comes next

The set above is the kit. Everything the five consuming applications need has landed, with
[@effected/app](/app) as the composition over `xdg`, `config-file` and `store` that the earlier ports were
building toward. Work now goes into hardening what exists against real consumers, and a new package earns
its place the same way the rest did — one of those five applications needs it.
