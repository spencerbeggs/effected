# @effected/lsp

Language Server Protocol base-protocol framing for Effect v4 —
`Content-Length` frames encoded by byte length and decoded incrementally —
a stdio launcher, `LspStdio`, that keeps stdout the wire and exits with the
code the specification requires, and a `./testing` subpath whose
`LspProbe` proves a Language Server bin boots and whose `LspProcess`
drives one frame by frame. They are the LSP twins of `@effected/mcp`'s
`McpStdio`, `McpProbe` and `McpProcess`.

## Why @effected/lsp

A tool that ships a Language Server bin needs the same packed-install
proof an MCP server gets from one `McpProbe.initialize` call: install the
tarball, start the bin, run a handshake, see it exit cleanly. Without a
kit tool, the LSP half gets hand-rolled — frames built with a template
string, written to stdin all at once, and the collected stdout
string-matched for the server's name.

That hand-rolled version has two traps. `Content-Length` counts **bytes**,
so a header built from `body.length` is right for ASCII and wrong the
first time a body carries a multi-byte character. And writing every frame
up front, then closing stdin, proves less than it seems: a server that
ignores `exit` and stops only when stdin closes passes, though under an
editor — which never closes the pipe first — it hangs.

A server written in Effect meets a third trap at launch: `runMain` reports
a failed program on stdout, outside every `Effect.provide` the program
applies, so a layer that fails to build prints its report onto the wire.
And a clean `exit` does not end the process while stdin is open.
`LspStdio` closes both.

## Install

```bash
npm install @effected/lsp effect
```

```bash
pnpm add @effected/lsp effect
```

Requires Node.js >=24.11.0. `effect` v4 is the only peer dependency.
Boundary tier: the main entry is pure, and `./testing` runs a child
process only through core's `ChildProcessSpawner`, provided by one
platform layer at the edge.

## What it exports

- **`LspFrame`** — `encode` (a message to a byte-counted frame);
  `decodeResult` and `decode` (every complete frame in a buffer, plus the
  bytes of an incomplete one); `decodeAllResult` and `decodeAll` (a
  collected stdout); `decodeStream` (a `Stream` of chunks to a `Stream` of
  messages).
- **`LspFrameError`** and **`LspFrameErrorCode`** — the typed failure of a
  malformed stream, with the rule it broke, the frame's stream position,
  and an excerpt of the frame's start.
- **`LspMessage`** — the JSON-RPC 2.0 message shape a frame body carries.
- **`LspStdio`** — `launch` (run a server program with stdout kept the
  wire), `exitCode` (the specification's exit code for a session) and
  `teardown` (the `runMain` teardown that ends the process), with the
  `LspSessionEnd` and `LspExitHost` types.
- **`@effected/lsp/testing`** — `LspProbe.initialize`, its
  `LspProbeOptions` and `LspProbeResult`; `LspProcess.spawn` and
  `LspProcessStderrUntilOptions`; and `LspTestFailure`.

## Reach for it when

- You ship a Language Server bin and need a packed-install test that
  proves it boots and completes the LSP lifecycle.
- You write a Language Server in Effect and run it over stdio.
- You test a Language Server bin message by message, or need to prove its
  stdout carried nothing but frames.
- You read or write LSP frames anywhere — a test client, a proxy, a log
  replay — and want byte-correct framing with a typed failure.

This is not an LSP server framework: the message loop and every handler
stay with whatever you serve the protocol with. `@effected/lsp` is a front end's sibling, like
`@effected/mcp` and `@effected/cli`, and nothing in the kit may depend on
it except an application.

See the [Getting Started guide](/lsp/getting-started) for the launcher,
the test clients and the framing functions.
