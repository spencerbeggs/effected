# Getting Started

Reach for `@effected/cli` the first time you run your own binary and wince at what it printed. Effect's defaults are tuned for a long-running service: log records carry a timestamp, a level and a fiber id, and an unhandled failure is reported by the runtime's *own* logger, on stdout. A CLI also has readers a service never has: a person at a colour terminal, an AI agent that wants plain text, and a CI log that reads certain lines as commands. This package handles all of that at the edge of the program, without importing a platform package, so the same code runs on Node, Bun and Deno.

It is **not** a CLI framework. `effect/cli` still owns argument parsing, flags, the command tree and help.

## Install

```bash
npm install @effected/cli @effected/env @effected/glob @effected/walker effect
```

```bash
pnpm add @effected/cli @effected/env @effected/glob @effected/walker effect
```

Requires Node.js >=24.11.0. The `@effected/*` packages and `effect` v4 are peers. The interactive screens in `@effected/cli/ui` also need `ink`, `react` and `@types/react`; the [prompts and screens guide](/cli/prompts) covers them.

## Your first task: wire a program

Here is the everyday goal. You have a `sync` command that reports progress and a result. You want it to look right at a terminal, stay plain for an agent or a pipe, put problems on stderr, and exit non-zero when something fails.

That takes one wiring, and every program built on this package uses it:

```ts
import { CliAudience, CliMessage, CliRuntime } from "@effected/cli";
import { NodeRuntime, NodeServices } from "@effect/platform-node";
import { Effect } from "effect";
import { Command } from "effect/cli";

const sync = Command.make("sync", {}, () =>
  Effect.gen(function* () {
    yield* CliMessage.info("syncing 2 repositories");
    yield* CliMessage.warning("acme/gadgets has no default branch");
    yield* CliMessage.success("synced 2 repositories");
  }),
);

// 1. Share the audience flags on the root command.
const root = Command.make("tool").pipe(Command.withSharedFlags(CliAudience.flags()), Command.withSubcommands([sync]));

// 2. Run it through CliAudience.run, and that through CliRuntime.main with an env.
NodeRuntime.runMain(
  CliRuntime.main(CliAudience.run(root, { version: "1.0.0" }), {
    platform: NodeServices.layer,
    env: {
      audienceEnvVar: "TOOL_AUDIENCE",
      stderrIsTerminal: Effect.sync(() => process.stderr.isTTY === true),
    },
  }),
);
```

```text
$ tool sync
ℹ syncing 2 repositories
⚠ acme/gadgets has no default branch
✓ synced 2 repositories
```

Each piece of that wiring does a specific job:

- **`CliAudience.flags()`** adds four shared flags: `--audience <human|agent|ci>` and the shorthands `--human`, `--agent` and `--ci`. A root command without them does not compile with `CliAudience.run`.
- **`CliAudience.run(root, { version })`** is `Command.run` with the audience flag read from the arguments *before* core parses them. A prompt that fires during parsing therefore already knows `--agent` was given.
- **`CliRuntime.main(program, options)`** assembles the whole program: the platform layer, failure reporting, a fresh exit-code cell and the logger, in the one order that reports every failure well.
- **`env`** tells `main` to build the environment services: who is running the program (from [`@effected/env`](/env)), what the terminal can do, the audience, the theme and editor links. Leave it out and nothing is themed, and the program never prompts.
- **`audienceEnvVar`** names a variable a user can set (`TOOL_AUDIENCE=human`) to override detection, for example a person working inside an agent's shell.
- **`stderrIsTerminal`** gives the real stderr TTY check. Core's `Stdio` reports only stdout, so without it stderr's colour mirrors stdout's.

The audience is decided once: a flag first, then the override variable, then an agent detected from the environment, then CI, else a human. The [audiences and output guide](/cli/output) covers each rule.

`CliMessage` writes one line each through `Console`, never the logger, so no log level silences it. `info` and `success` go to stdout, and `warning` and `failure` to stderr. Only the glyph is painted, and only when the stream has colour. An agent always gets the glyph and the text with no escape sequences, even with `FORCE_COLOR` set.

### Print more than a line

For tables, lists, trees and counts, build a document with [`Doc`](/cli/api/class/doc) and print it. `Doc.print` picks the renderer from the audience: painted for a person, plain for an agent, and GitHub's log format under GitHub Actions:

```ts
import { Doc, Status } from "@effected/cli";
import { Effect } from "effect";

const report = Effect.gen(function* () {
  yield* Doc.print([
    Doc.table(
      [{ header: "Repository" }, { header: "Files", align: "right" }],
      [
        ["acme/widgets", "12"],
        ["acme/gadgets", "3"],
      ],
    ),
    Doc.counts({
      layout: "inline",
      counters: [
        Doc.counter(Status.core, "success", { key: "synced", label: "synced", n: 2 }),
        Doc.counter(Status.core, "failure", { key: "failed", label: "failed", n: 0 }),
      ],
      durationMs: 1234,
    }),
  ]);
});
```

```text
Repository    Files
------------  -----
acme/widgets     12
acme/gadgets      3
2/2 synced (1.2s)
```

Inside a program run by `CliRuntime.main` with `env`, the services `Doc.print` needs are already provided. The [audiences and output guide](/cli/output) covers every block and renderer.

## Keep diagnostics off stdout

`Effect.log` is a diagnostic, not the program's output. Under `CliRuntime.main` the logger is [`CliLogger`](/cli/api/class/clilogger), which writes plain lines with no timestamp, level or fiber id, and routes **every level to stderr** by default. The program's real output is whatever it writes with `Console.log`, `CliMessage` or `Doc.print`. So `tool sync > report.txt` captures the result, and the diagnostics still show on the terminal.

On its own, outside `main`, the logger looks like this:

```ts with-api
import { CliLogger } from "@effected/cli";
import { Console, Effect } from "effect";

const sync = Effect.gen(function* () {
  yield* Effect.logInfo("syncing acme/widgets"); // a diagnostic, not the result
  yield* Console.log("synced 3 repos"); // the program's actual output
  yield* Effect.logError("one failed: acme/widgets");
});

Effect.runPromise(sync.pipe(Effect.provide(CliLogger.layer())));
// stdout: synced 3 repos
// stderr: syncing acme/widgets
// stderr: one failed: acme/widgets
```

`CliLogger` sends a record to stderr when its level is at or above `stderrFrom`, which **defaults to `"All"`**. The comparison is ordinal rather than an equality test against a list of level names, so a level added upstream lands on the right stream without a change here. The logger reads the `Console` off the fiber to write, which is why it needs no platform package, and why a test can provide a capturing `Console` instead of stubbing a global.

For a diagnostics *level*, NDJSON for agents and a log file, pass `env.log` to `main`. That is [`CliLog`](/cli/api/class/clilog), covered in the [audiences and output guide](/cli/output#diagnostics-with-clilog).

## Common operations

Each snippet below is complete and built only from the package's real exports.

### Prefix or reshape every line

`render` turns a log message into the string that gets written. It receives `unknown` because `Effect.log("synced", 3, "repos")` is variadic and hands the logger an array. The default joins an array with spaces and `String`s anything else. Override it when your tool wants a prefix or a marker:

```ts with-api
import { CliLogger } from "@effected/cli";
import { Effect } from "effect";

const program = Effect.gen(function* () {
  yield* Effect.log("synced", 3, "repos");
  yield* Effect.logError("one failed");
});

const layer = CliLogger.layer({
  stderrFrom: "Error",
  render: (message) => (Array.isArray(message) ? `› ${message.map(String).join(" ")}` : `› ${String(message)}`),
});

Effect.runPromise(program.pipe(Effect.provide(layer)));
// stdout: › synced 3 repos
// stderr: › one failed
```

A custom `render` receives the message's string parts already sanitised, and owns its own output from there, colour included.

### Move the stderr threshold

Some tools' output *is* their log lines rather than a separate document written with `Console.log`. For those, narrow the threshold with `stderrFrom`, so only `Error` and above cross to stderr and everything below stays on stdout:

```ts with-api
import { CliLogger } from "@effected/cli";
import { Effect, References } from "effect";

const program = Effect.gen(function* () {
  yield* Effect.logInfo("scanning workspace");
  yield* Effect.logWarning("skipping packages/legacy");
  yield* Effect.logError("workspace root not found");
}).pipe(Effect.provideService(References.MinimumLogLevel, "Debug"));

Effect.runPromise(program.pipe(Effect.provide(CliLogger.layer({ stderrFrom: "Error" }))));
// stdout: scanning workspace
// stdout: skipping packages/legacy
// stderr: workspace root not found
```

`References.MinimumLogLevel` is the reference that decides which records are emitted at all. Provide it as a service. There is no `Logger.withMinimumLogLevel` on the v4 line, and reaching for one is the usual first wrong turn.

### Compose the logger into a set you already have

When you are assembling the logger set yourself, a file logger alongside the terminal one say, reach for `CliLogger.make`, which hands you the `Logger` itself:

```ts with-api
import { CliLogger } from "@effected/cli";
import { Effect, Logger } from "effect";

const Loggers = Logger.layer([CliLogger.make({ stderrFrom: "Warn" })]);

Effect.runPromise(Effect.log("ready").pipe(Effect.provide(Loggers)));
// stdout: ready
```

### Report a failure through your own logger

`CliRuntime.main` does this for you. Without `main`, apply [`CliRuntime.reportFailures`](/cli/api/class/cliruntime) **inside** your program. It catches the failure there, renders it through the ambient logger and re-fails with a marked error. Because the catch happens inside, the report goes through `CliLogger` and lands on stderr, where a platform `runMain`'s own report would have gone through Effect's default logger on stdout:

```ts with-api
import { CliLogger, CliRuntime } from "@effected/cli";
import { Effect } from "effect";

const program = Effect.fail(new Error("no package.json in /tmp/project"));

const main = program.pipe(CliRuntime.reportFailures({ exitCode: 2 }), Effect.provide(CliLogger.layer()));

Effect.runPromiseExit(main).then((exit) => console.log(exit._tag));
// stderr: [FAIL] Error: no package.json in /tmp/project
// Failure
```

The program still fails, because swallowing the failure would make a broken run exit `0`. `exitCode` is used when the error does not carry a code of its own. An error already marked with `Runtime.errorExitCode` keeps its code.

The report is [`CliFailure`](/cli/api/class/clifailure)'s document of the failure. Outside `main`'s environment there is no terminal to ask, so it renders plain, with `[FAIL]` in place of the status glyph. Under `main` with `env` it is painted for a person and plain for an agent or a CI log.

### Turn a decode failure into sentences

[`SchemaIssueRenderer.render`](/cli/api/class/schemaissuerenderer) flattens a `SchemaIssue` tree into one line per rejected value. Decode with `errors: "all"` and `onExcessProperty: "error"` to collect everything a user got wrong in one pass, rather than one mistake per run:

```ts with-api
import { SchemaIssueRenderer } from "@effected/cli";
import { Effect, Schema } from "effect";

const Config = Schema.Struct({
  name: Schema.String,
  retries: Schema.Number,
});

const decoded = Schema.decodeUnknownEffect(Config)(
  { name: "app", retries: "three", rulesetz: true },
  { errors: "all", onExcessProperty: "error" },
);

const program = decoded.pipe(
  Effect.catchTag("SchemaError", (error) => Effect.succeed(SchemaIssueRenderer.render(error.issue))),
);

Effect.runPromise(program).then(console.log);
// [ 'unknown key at rulesetz', 'Expected number at retries' ]
```

The renderer is a thin wrapper over core's `SchemaIssue.makeFormatterStandardSchemaV1`, which is real but hard to find: it lives on `SchemaIssue` rather than on `SchemaError`, it is named `makeFormatter*`, and `SchemaError.message` does not use it. On top of it the renderer removes duplicate lines (a union reports the same unknown key once per member). It also rephrases core's `"Expected no excess property"`, which names the schema's rule, as `unknown key`, which names the user's mistake. A schema failure that reaches the default failure report is drawn as a tree of the same rejected values.

### Exit non-zero for findings, not crashes

A command whose non-zero exit is a *result*, such as a linter that found problems, has not failed. It calls `CliExit.set(code)` from a handler that still **succeeds**, and `CliRuntime.main` turns the code into a real exit once the program ends:

```ts with-api
import { CliExit, CliRuntime } from "@effected/cli";
import { NodeServices } from "@effect/platform-node";
import { Console, Effect } from "effect";

const findings = Effect.gen(function* () {
  yield* Console.log("2 problems found");
  // Findings, not a crash: the handler still succeeds. CliExit.set records
  // the code CliRuntime.main turns into a real exit once the program ends.
  yield* CliExit.set(1);
});

const main = CliRuntime.main(findings, { platform: NodeServices.layer });
```

`CliExit` is a `Context.Service`, not a reference, so forgetting to run under `CliRuntime.main` is a type error, never a silently ignored global. `CliExit.layer` mints a **fresh** cell on every provide (`Layer.fresh`), and `main` provides one for you. **Do not provide `CliExit.layer` yourself inside a program run under `CliRuntime.main`.** A second provide creates a second, unrelated cell, and `CliExit.set` calls against it never reach the one `main` reads back, so a findings run silently exits `0`.

This exists because `process.exitCode` cannot be trusted to reach teardown: Node's own `runMain` skips `process.exit(0)` on success, and `process.exit(n)` from inside a handler skips every finalizer. Turning the code into a failure instead routes it through core's `defaultTeardown` like any other error, with finalizers intact, on any runtime.

### Share one colour decision with core's help text

Under `CliRuntime.main` with `env`, help text and parse errors already follow the same colour decision as everything else. Without `env`, [`CliColor.formatterLayer`](/cli/api/class/clicolor) hands that decision to `effect/cli`'s own `CliOutput.Formatter`:

```ts
import { CliColor } from "@effected/cli";
import { NodeServices } from "@effect/platform-node";
import { Layer } from "effect";

// Feeds Stdio from the platform layer into the colour decision, and keeps
// NodeServices' own services available too.
const Platform = CliColor.formatterLayer().pipe(Layer.provideMerge(NodeServices.layer));
```

The decision is `@effected/env`'s colour level for stdout, so it follows Node's precedence. `FORCE_COLOR` decides first and beats `NO_COLOR`: `1`, `2` or `3` turn colour on even in a pipe, and `0` turns it off. Otherwise there is no colour when stdout is not a terminal. On a terminal, a non-empty `NO_COLOR`, `NODE_DISABLE_COLORS` or `TERM=dumb` turns it off. Each call to `CliColor.formatterLayer()` mints a fresh layer, so bind the result to a `const`.

## Handling errors

This package's own errors are the ones a prompt raises: [`Cancelled`](/cli/api/class/cancelled) (exit `130`) and [`NotInteractive`](/cli/api/class/notinteractive) (exit `64`), each reported as one fixed line. Everything else is control over how *your* failures leave the program.

Under `CliRuntime.main`, fail with the error and let the report render it. Do not print a failure yourself before failing with it: the report would print it a second time. To control the rendering, give an error class a [`CliDoc`](/cli/api/variable/clidoc) method that returns its document, or pass `main` a `render` option. The [audiences and output guide](/cli/output#failure-reports) shows both.

Outside `main` and `reportFailures`, a command that prints its own diagnostics still needs a non-zero exit and no second report from the runtime. `CliRuntime.reported` marks an error as already reported and attaches an exit code:

```ts
import { CliRuntime, ConfigIssueRenderer } from "@effected/cli";
import type { ConfigFileShape } from "@effected/config-file";
import { Effect } from "effect";

declare const configFile: ConfigFileShape<{ readonly name: string }>;

const load = configFile.load.pipe(
  Effect.catchTag("ConfigValidationError", (error) =>
    Effect.gen(function* () {
      yield* Effect.logError(String(error));
      for (const line of ConfigIssueRenderer.render(error)) yield* Effect.logError(`  ${line}`);

      // Re-fail, or the handler SUCCEEDS and the CLI exits 0 on invalid config.
      return yield* Effect.fail(CliRuntime.reported(error, 78));
    }),
  ),
);
```

Two details are worth internalizing before you rely on them. The marker `Runtime.errorReported` has **inverted polarity relative to its name**: `false` is what suppresses the runtime's own report, because the marker means "should this be reported". The intuitive `true` produces exactly the double report it was meant to prevent. And an **interrupt is never reported**: an interrupt-only cause passes straight through, and the default teardown maps it to `130`.
