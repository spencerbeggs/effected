# Getting Started

Reach for `@effected/cli` the first time you run your own binary and wince at what it printed. Effect's defaults are tuned for a long-running service: log records carry a timestamp, a level and a fiber id, and an unhandled failure is reported by the runtime's *own* logger on stdout. Both are correct for something being scraped by a log collector and wrong for a tool a person is watching. This package fixes exactly those defaults — plain lines, diagnostics on stderr, failures rendered by the logger *you* installed — and it does it without importing a platform package, so the same code runs on Node, Bun and Deno.

It is **not** a CLI framework. `effect/unstable/cli` still owns argument parsing, flags, the command tree and help.

## Install

```bash
npm install @effected/cli effect
```

```bash
pnpm add @effected/cli effect
```

Requires Node.js >=24.11.0. `effect` v4 is a peer dependency; the package adds no runtime dependencies of its own. `@effected/config-file` is an optional peer, needed only if you use [`ConfigIssueRenderer`](/cli/api/class/configissuerenderer).

## Your first task: make a program's output look like a tool

Here is the everyday goal. You have a `sync` command that reports its result and complains when something goes wrong, and you want the result on stdout, the complaint on stderr, and nothing but the message on either line — so `mytool sync > report.txt` captures the result and still shows the failure on the terminal.

Start from what the defaults give you. `Effect.log` is an `Info` record and `Effect.logError` is an `Error` record; with no logger installed, both print through Effect's structured default. Installing [`CliLogger`](/cli/api/class/clilogger) replaces it — `Logger.layer` replaces rather than merges, so nothing is emitted twice:

```ts with-api
import { CliLogger } from "@effected/cli";
import { Console, Effect } from "effect";

const sync = Effect.gen(function* () {
  yield* Effect.logInfo("syncing acme/widgets"); // a diagnostic, not the result
  yield* Console.log("synced 3 repos"); // the program's actual output
  yield* Effect.logError("one failed: acme/widgets");
});

Effect.runPromise(sync.pipe(Effect.provide(CliLogger.layer())));
// stdout: synced 3 repos
// stderr: syncing acme/widgets
// stderr: one failed: acme/widgets
```

Two things happened, and only one of them is obvious. The obvious one is the formatting: no timestamp, no level, no fiber id, so a formatted table or a summary block survives being logged. The second is the **stream split**. `CliLogger` sends a record to stderr when its level is at or above `stderrFrom`, which **defaults to `"All"`** — a CLI's stdout is its product, so every log level is a diagnostic unless you narrow the threshold, and the program's real output is written with `Console.log` instead. The comparison is ordinal rather than an equality test against a list of level names, so a level above the threshold — including one added upstream — lands on stderr without a change here.

The logger reads the `Console` off the fiber to write, which is why it needs no platform package and why the split is testable: a test provides a capturing `Console` instead of stubbing a global.

### Wire it into a real binary

In an actual program the logger belongs in the layer you provide to the *whole* application, merged with the rest rather than provided beneath it. Merged, it also covers lines emitted during layer construction — which is exactly where a startup failure prints:

```ts
import { CliLogger, CliRuntime } from "@effected/cli";
import { NodeRuntime } from "@effect/platform-node";
import { Effect, Layer } from "effect";

declare const AppLive: Layer.Layer<never>;
declare const sync: Effect.Effect<void>;

const MainLive = Layer.mergeAll(AppLive, CliLogger.layer());

NodeRuntime.runMain(sync.pipe(CliRuntime.reportFailures(), Effect.provide(MainLive)));
```

You still call your own platform's runner. `@effected/cli` never wraps `runMain`, because doing so would bake a platform choice into a library that has no business making one.

## Common operations

Each snippet below is complete and built only from the package's real exports.

### Prefix or reshape every line

`render` turns a log message into the string that gets written. It receives `unknown` because `Effect.log("synced", 3, "repos")` is variadic and hands the logger an array; the default joins an array with spaces and `String`s anything else. Override it when your tool wants a prefix or a marker:

```ts with-api
import { CliLogger } from "@effected/cli";
import { Effect } from "effect";

const program = Effect.gen(function* () {
  yield* Effect.log("synced", 3, "repos");
  yield* Effect.logError("one failed");
});

const layer = CliLogger.layer({
  render: (message) => (Array.isArray(message) ? `› ${message.map(String).join(" ")}` : `› ${String(message)}`),
});

Effect.runPromise(program.pipe(Effect.provide(layer)));
// stdout: › synced 3 repos
// stderr: › one failed
```

### Move the stderr threshold

Some tools' output *is* their log lines rather than a separate document written with `Console.log` — for those, narrow the threshold with `stderrFrom` so only `Error` and above cross to stderr, and everything below stays on stdout:

```ts with-api
import { CliLogger } from "@effected/cli";
import { Effect, References } from "effect";

const program = Effect.gen(function* () {
  yield* Effect.logInfo("scanning workspace");
  yield* Effect.logWarning("skipping packages/legacy");
  yield* Effect.logError("workspace root not found");
}).pipe(Effect.provideService(References.MinimumLogLevel, "Debug"));

Effect.runPromise(program.pipe(Effect.provide(CliLogger.layer({ stderrFrom: "Error" }))));
// stdout: scanning workspace
// stdout: skipping packages/legacy
// stderr: workspace root not found
```

`References.MinimumLogLevel` is the reference that decides which records are emitted at all. Provide it as a service — there is no `Logger.withMinimumLogLevel` on the v4 line, and reaching for one is the usual first wrong turn.

### Compose the logger into a set you already have

`CliLogger.layer` is the common path. When you are assembling the logger set yourself — a file logger alongside the terminal one, say — reach for `CliLogger.make`, which hands you the `Logger` itself:

```ts with-api
import { CliLogger } from "@effected/cli";
import { Effect, Logger } from "effect";

const Loggers = Logger.layer([CliLogger.make({ stderrFrom: "Warn" })]);

Effect.runPromise(Effect.log("ready").pipe(Effect.provide(Loggers)));
// stdout: ready
```

### Report a failure through your own logger

[`CliRuntime.reportFailures`](/cli/api/class/cliruntime) catches inside your program, renders the failure through the ambient logger, and re-fails with a marked error. Because the catch happens *inside*, the report goes through `CliLogger` and lands on stderr — where a platform `runMain`'s own report would have gone through Effect's default logger, on stdout:

```ts with-api
import { CliLogger, CliRuntime } from "@effected/cli";
import { Effect } from "effect";

const program = Effect.fail(new Error("no package.json in /tmp/project"));

const main = program.pipe(CliRuntime.reportFailures({ exitCode: 2 }), Effect.provide(CliLogger.layer()));

Effect.runPromiseExit(main).then((exit) => console.log(exit._tag));
// stderr: Error: no package.json in /tmp/project
// Failure
```

The program still fails — swallowing the failure would make a broken run exit `0`. `exitCode` is the code used when the error does not carry one of its own; an error already marked with `Runtime.errorExitCode` keeps it.

### Turn a decode failure into sentences

[`SchemaIssueRenderer.render`](/cli/api/class/schemaissuerenderer) flattens a `SchemaIssue` tree into one line per rejected value. Decode with `errors: "all"` and `onExcessProperty: "error"` to collect everything a user got wrong in a single pass rather than one mistake per run:

```ts with-api
import { SchemaIssueRenderer } from "@effected/cli";
import { Effect, Schema } from "effect";

const Config = Schema.Struct({
  name: Schema.String,
  retries: Schema.Number,
});

const decoded = Schema.decodeUnknownEffect(Config)(
  { name: "app", retries: "three", rulesetz: true },
  { errors: "all", onExcessProperty: "error" },
);

const program = decoded.pipe(
  Effect.catchTag("SchemaError", (error) => Effect.succeed(SchemaIssueRenderer.render(error.issue))),
);

Effect.runPromise(program).then(console.log);
// [ 'unknown key at rulesetz', 'Expected number at retries' ]
```

The renderer is a thin, deliberate wrapper over core's `SchemaIssue.makeFormatterStandardSchemaV1`, which is real but near-undiscoverable — it lives on `SchemaIssue` rather than on `SchemaError`, it is named `makeFormatter*`, and `SchemaError.message` does not use it. On top of it the renderer deduplicates lines (a union reports the same unknown key once per member) and rephrases core's `"Expected no excess property"`, which names the schema's rule, as `unknown key`, which names the user's mistake.

### Assemble a whole program with `CliRuntime.main`

`reportFailures` is the combinator; `CliRuntime.main` is the whole recipe — the platform layer, a fresh [`CliExit`](/cli/api/class/cliexit), failure reporting and the logger, composed in the one order that reports every failure well. A command whose non-zero exit is a *result* rather than a crash — a linter that found problems, say — calls `CliExit.set(code)` from a handler that still **succeeds**:

```ts with-api
import { CliExit, CliRuntime } from "@effected/cli";
import { NodeServices } from "@effect/platform-node";
import { Console, Effect } from "effect";

const findings = Effect.gen(function* () {
  yield* Console.log("2 problems found");
  // Findings, not a crash: the handler still succeeds. CliExit.set records
  // the code CliRuntime.main turns into a real exit once the program ends.
  yield* CliExit.set(1);
});

const main = CliRuntime.main(findings, { platform: NodeServices.layer });
```

`CliExit` is a `Context.Service`, not a reference, so forgetting to run under `CliRuntime.main` is a type error, never a silently-ignored global — and `CliExit.layer` mints a **fresh** cell on every provide (`Layer.fresh`), so `main` provides one for you. **Do not provide `CliExit.layer` yourself inside a program run under `CliRuntime.main`** — a second provide creates a second, unrelated cell, and `CliExit.set` calls against it never reach the one `main` reads back, so a findings run silently exits `0`.

This exists because `process.exitCode` cannot be trusted to reach teardown: Node's own `runMain` skips `process.exit(0)` on success, and `process.exit(n)` from inside a handler skips every finalizer. Turning the code into a failure instead routes it through core's `defaultTeardown` like any other error, with finalizers intact, on any runtime — and `reportFailures` never renders it, because there is nothing to say: only an exit code a successful program already chose.

### Match core's colour decision with `CliColor`

[`CliColor.enabled`](/cli/api/class/clicolor) follows the [no-color.org](https://no-color.org) rule: off when stdout is not a terminal, or when `NO_COLOR` is set to any non-empty value (`FORCE_COLOR` is ignored, matching core's own formatter). [`CliColor.formatterLayer`](/cli/api/class/clicolor) hands that same decision to `effect/unstable/cli`'s own `CliOutput.Formatter`, so help text, parse errors and anything you render agree with each other:

```ts
import { CliColor } from "@effected/cli";
import { NodeServices } from "@effect/platform-node";
import { Layer } from "effect";

// Feeds Stdio from the platform layer into CliColor's decision, and keeps
// NodeServices' own services available too.
const Platform = CliColor.formatterLayer().pipe(Layer.provideMerge(NodeServices.layer));
```

Each call to `CliColor.formatterLayer()` mints a fresh layer — bind the result to a `const`, as above, or the decision is re-read every time it is provided.

### Test a built bin with `CliTest`

`@effected/cli/testing` is a **separate entrypoint** — nothing reachable from `@effected/cli` imports it, so it never reaches a CLI's own runtime bundle. `CliTest.sandbox` mints a hermetic temp directory with a fresh `HOME` and XDG tree; `CliTest.run` spawns a built bin inside it and hands back its exit code and both streams as data:

```ts
import { CliTest } from "@effected/cli/testing";
import * as NodeServices from "@effect/platform-node/NodeServices";
import { assert, describe, it } from "@effect/vitest";
import { Effect } from "effect";

describe("mytool", () => {
  it.effect("exits 1 when it finds a problem", () =>
    Effect.gen(function* () {
      const sandbox = yield* CliTest.sandbox({ path: process.env.PATH ?? "" });
      const result = yield* CliTest.run("./dist/mytool.js", ["check"], {
        sandbox,
        execPath: process.execPath,
      });
      assert.strictEqual(result.exitCode, 1);
      assert.include(result.stdout, "2 problems found");
    }).pipe(Effect.scoped, Effect.provide(NodeServices.layer)),
  );
});
```

**When `stdin` is omitted, or passed as `""`, the child receives an already-ended empty input, never an open pipe** — core's default `"pipe"` stdio stays open until something writes to and ends it, so a stdin-reading bin cannot hang the test.

## Handling errors

This package raises **no errors of its own** — it is presentation, and a package that renders other people's failures must not invent new ones. What it gives you instead is control over how a failure leaves your program.

`CliRuntime.reportFailures` handles the unhandled case. When a command reports its *own* diagnostics — a `validate` command printing every bad key, say — you want the report but not a second one from the runtime, and you still need the process to exit non-zero. That is what `CliRuntime.reported` is for: it marks an error as already reported and attaches an exit code.

```ts
import { CliRuntime, ConfigIssueRenderer } from "@effected/cli";
import type { ConfigFileShape } from "@effected/config-file";
import { Effect } from "effect";

declare const configFile: ConfigFileShape<{ readonly name: string }>;

const load = configFile.load.pipe(
  Effect.catchTag("ConfigValidationError", (error) =>
    Effect.gen(function* () {
      yield* Effect.logError(String(error));
      for (const line of ConfigIssueRenderer.render(error)) yield* Effect.logError(`  ${line}`);

      // Re-fail, or the handler SUCCEEDS and the CLI exits 0 on invalid config.
      return yield* Effect.fail(CliRuntime.reported(error, 78));
    }),
  ),
);
```

That pattern is for a program run **without** `CliRuntime.main` or `reportFailures`. Under either, do not print the failure yourself: `reportFailures` renders every error except a `ShowHelp`, a `CliError.UserError` whose reported mark is `false` (one `Command.runWith` already printed, or one you marked with `reported`) and the `CliExit` sentinel, so a failure you logged and then marked would print twice. Fail with the error and put the multi-line rendering in the `render` option instead — the [multi-line failure pattern](/cli/advanced#rendering-a-multi-line-failure) in the advanced guide shows it.

Two details are worth internalizing before you rely on them. The marker `Runtime.errorReported` has **inverted polarity relative to its name** — `false` is what suppresses the runtime's own report, because the marker means "should this be reported"; the intuitive `true` produces exactly the double report it was meant to prevent. And an **interrupt is never reported**: `reportFailures` passes an interrupt-only cause straight through, since it is not a failure anyone wants rendered and the default teardown already maps it to `130`.
