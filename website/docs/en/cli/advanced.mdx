# Advanced

## The bug this package exists to prevent

Picture a tool that has been carefully built. It installs a CLI logger, so its output is plain lines. It validates its config with a schema. It exits non-zero when something is wrong. Every success path is right, every test passes, and then a user runs it with a typo in their config file and gets `[00:33:56.619] ERROR (#2): ConfigValidationError: Config validation failed` — **on stdout**, in the format the logger was installed to replace, naming a file but not the key.

Nothing in that program is visibly wrong. The report came from the platform's `runMain`, which composes its reporting `tapCause` *around* the already-provided effect, so it runs **outside** the layers the program installed and prints through Effect's default logger. The key went unnamed because a decode failure is a structured tree, and `SchemaError.message` does not use the formatters core ships for it. Both defects are invisible from the call site and both are only discovered by running the binary and reading what a person sees.

`@effected/cli` is the presentation surface that fixes that class of defect and nothing else: [`CliLogger`](/cli/api/class/clilogger), [`CliRuntime`](/cli/api/class/cliruntime) (including `CliRuntime.main`), `CliExit`, `CliColor`, [`SchemaIssueRenderer`](/cli/api/class/schemaissuerenderer) and [`ConfigIssueRenderer`](/cli/api/class/configissuerenderer) — plus a `./testing` subpath exporting `CliTest`, test tooling that never enters a CLI's own runtime import graph. This guide covers the composition rules, the exit-code semantics, findings that exit non-zero without crashing, the reference that can move the stream split, the optional-peer discipline, and how to test the parts that silently regress. It assumes the basics from the [getting-started guide](/cli/getting-started).

## How it composes with Effect

Almost nothing here is a service. `CliLogger.layer` produces a `Layer.Layer<never>`, `CliRuntime.reportFailures` is a plain combinator that preserves your `R`, `CliColor` is pure functions and a layer factory, and both renderers are pure functions. The logger reaches for `Console.Console`, which is a `Context.Reference` carrying `globalThis.console` as its default — a reference never lands in the requirements channel, so a consumer's layer stack is untouched. `CliExit` is the one deliberate exception: a real `Context.Service`, so that forgetting to run a findings command under `CliRuntime.main` is a type error rather than a silently-ignored default.

There is also **no platform package**, required or optional. That is a deliberate tier boundary: the moment `@effect/platform-node` appeared here the package would stop being usable from Bun and Deno for no benefit. You call your own runner.

Two placement rules follow from that, and getting either wrong reintroduces the original bug.

**Merge the logger layer; do not provide it beneath.** `Layer.mergeAll(AppLive, CliLogger.layer())` puts the logger in scope for the whole program *including layer construction*, which is exactly where a startup failure prints. Providing it beneath a sub-effect leaves the construction phase on the default logger.

**Apply `reportFailures` inside, before `Effect.provide`.** The order in the pipe is the entire fix:

```ts
import { CliLogger, CliRuntime } from "@effected/cli";
import { NodeRuntime } from "@effect/platform-node";
import { Effect, Layer } from "effect";

declare const AppLive: Layer.Layer<never>;
declare const program: Effect.Effect<void>;

const MainLive = Layer.mergeAll(AppLive, CliLogger.layer());

// reportFailures FIRST — it must be inside the effect the layers are provided to.
NodeRuntime.runMain(program.pipe(CliRuntime.reportFailures(), Effect.provide(MainLive)));
```

Within the kit, `@effected/cli` sits beside [`@effected/app`](/app) rather than under it: `app` is the control plane — directories, state, cache, config — and `cli` is the presentation boundary. Neither imports the other, and **nothing in the kit may depend on this package except an application**. A library that reaches for CLI output has made a decision that belongs to the program at the top.

## Exit codes, and the two markers that carry them

`reportFailures` does not swallow the failure it reported — swallowing it would make a broken run exit `0`. It re-fails with an `Error` carrying two of core's own markers, which is how the exit code is settled without a platform import.

`Runtime.errorExitCode` is the process exit code `defaultTeardown` reads off the squashed error. An error that **already carries one keeps it**: that was a deliberate choice by whatever raised it. The `exitCode` option is a fallback for errors that chose nothing, and so is `usageExitCode` for a `CliError.UserError` — `CliRuntime.reported(userError, 3)` exits `3`. The one exception is a `ShowHelp`, whose code `reportFailures` always decides: `usageExitCode` when it carries parse errors, `0` when it does not.

```ts with-api
import { CliRuntime } from "@effected/cli";
import { Runtime } from "effect";

// A command that reported its own diagnostics marks its error and picks a code.
const marked = CliRuntime.reported(new Error("config not found"), 66);

console.log(Runtime.getErrorExitCode(marked));
// 66

console.log(Runtime.getErrorExitCode(new Error("something else")));
// 1
```

That second line is the trap the implementation works around. `Runtime.getErrorExitCode` answers `1` both for an error deliberately marked `1` and for an unmarked one, so it cannot be used alone to decide whether the `exitCode` option applies. `reportFailures` tests for the marker with `Runtime.errorExitCode in error` first, keeping "the error chose its code" distinct from "nothing chose".

`Runtime.errorReported` is the second marker, and **its polarity is inverted relative to its name**. It means "should this be reported", so `false` is what suppresses the runtime's own report. The intuitive reading — `errorReported: true`, "I have reported it, stay quiet" — produces exactly the double report the marker exists to prevent. `CliRuntime.reported` is exported so a program that prints its own diagnostics gets both marks right without rediscovering that.

```ts with-api
import { CliLogger, CliRuntime } from "@effected/cli";
import { Effect } from "effect";

const validate = Effect.gen(function* () {
  yield* Effect.logError("config invalid: 2 problems");
  yield* Effect.logError("  unknown key at variables.keep.KEEP_ME");

  // Already reported, so mark it — otherwise the runtime prints it a second
  // time in the format CliLogger exists to replace.
  return yield* Effect.fail(CliRuntime.reported(new Error("config invalid"), 78));
});

Effect.runPromiseExit(validate.pipe(Effect.provide(CliLogger.layer()))).then((exit) => console.log(exit._tag));
// stderr: config invalid: 2 problems
// stderr:   unknown key at variables.keep.KEEP_ME
// Failure
```

Note that this program does **not** apply `reportFailures`; it reports itself. That is the only place this pattern belongs. Under `CliRuntime.main` or `reportFailures`, do not print the failure yourself: `reportFailures` renders every error except a `ShowHelp`, a `CliError.UserError` whose reported mark is `false` and the `CliExit` sentinel, so a failure you logged and then marked would print twice. Fail with the error and put the multi-line rendering in the `render` option instead — [Rendering a multi-line failure](#rendering-a-multi-line-failure) below shows it.

## `reportFailures` never renders `ShowHelp`

`effect/unstable/cli`'s `Command.runWith` already printed the help text, or the parse errors, before a `CliError.ShowHelp` reaches `reportFailures` — rendering it a second time produces nothing but a stray "Help requested" line. `reportFailures` special-cases it: a `ShowHelp` carrying parse errors is remapped to the `usageExitCode` option (default `64`, BSD `EX_USAGE`); a bare `--help` invocation or a root command with no arguments — a `ShowHelp` with no errors — keeps exit `0`.

A `CliError.UserError` a handler fails with gets the same treatment. `Command.runWith` renders it through its `CliOutput` formatter and flips its `Runtime.errorReported` mark to `false` before re-failing, so `reportFailures` skips it and exits `usageExitCode` (default `64`) — unless the error carries its own `Runtime.errorExitCode`, which it keeps. `reportFailures` cannot tell that `UserError` from one you marked with `CliRuntime.reported`, because both carry the same `false` mark: **a `CliError.UserError` marked with `reported` is treated as already printed and is not rendered** — use a different error type if the program has not printed it. With runWith's `renderErrors: false`, runWith prints nothing, the mark stays set, and `reportFailures` renders the `UserError` like any other failure, with the `exitCode` fallback.

```ts
import { CliRuntime } from "@effected/cli";

// A ShowHelp carrying parse errors exits 64 by default; override it per program:
const reported = program.pipe(CliRuntime.reportFailures({ usageExitCode: 2 }));
```

## `CliRuntime.main`: the whole recipe, in the one order that reports every failure well

`reportFailures` is the combinator that fixes *where* a failure is reported. `CliRuntime.main` composes the whole program around it — a fresh `CliExit`, the platform layer, failure reporting, and the logger, each in a specific position for a reason:

```ts
import { CliColor, CliExit, CliRuntime } from "@effected/cli";
import { NodeRuntime, NodeServices } from "@effect/platform-node";
import { Console, Effect, Layer } from "effect";
import { Command, Flag } from "effect/unstable/cli";

const check = Command.make("check", { strict: Flag.Boolean("strict").pipe(Flag.withDefault(false)) }, (config) =>
  Effect.gen(function* () {
    const problems = config.strict ? ["missing changeset", "unpinned dependency"] : ["missing changeset"];
    for (const problem of problems) yield* Console.log(problem);
    if (problems.length > 0) yield* CliExit.set(1);
  }),
);

const Platform = CliColor.formatterLayer().pipe(Layer.provideMerge(NodeServices.layer));

NodeRuntime.runMain(CliRuntime.main(Command.run(check, { version: "1.0.0" }), { platform: Platform }));
```

1. `CliExit.layer` is provided first — `Layer.fresh`, so `main` always builds a brand-new cell rather than sharing one across provides.
2. The **platform layer is provided inside `reportFailures`** — a layer-build failure (`HOME` unset, say) renders as one line through your logger with the fallback exit code, rather than escaping to the runtime's own stack trace.
3. **The logger is provided outermost**, so it is present whichever branch failed — even a failure during platform construction.

`CliExit.set` takes an integer in `0..255`, the range a POSIX exit status can carry; anything else (`256`, `1.5`, `NaN`) dies as a defect naming the value, and `main` re-checks a code written to the cell directly. `256` would otherwise wrap to exit `0` and pass a run with findings. A program **failure** beats findings: `main` reads the cell only after the program succeeds, so a failed run exits with the failure's code.

After the program body runs to completion, `main` reads the `CliExit` cell; a non-zero value becomes a failure carrying a private `ExitRequested` sentinel, marked exactly like `CliRuntime.reported` marks one. `reportFailures` never renders it — there is nothing to say, only an exit code a *successful* program already chose — and nothing outside this package can construct or match it.

**Never provide `CliExit.layer` yourself inside a program run under `CliRuntime.main`.** `main` already provides one; a second provide anywhere in the program tree mints a second, unrelated cell (layers memoize by reference, and `Layer.fresh` defeats that memoization deliberately), so `CliExit.set` calls against it never reach the cell `main` reads back — the findings a handler recorded silently vanish and the run exits `0`.

### Why not `process.exitCode`?

Two reasons, and neither is about ordering. **Portability**: `process.exitCode` is a Node global, and it works there only because Node's own `runMain` skips `process.exit(0)` on success — it calls `process.exit` only when the fiber received a signal or its own exit code is non-zero — so the field survives until Node exits on its own. A program on another runtime has no such field, and a library that writes it has chosen a platform for its caller. **Finalizers**: the tempting alternative, `process.exit(n)` called directly from a handler, ends the process on the spot and skips every finalizer outright. Turning the code into a failure routes it through core's `defaultTeardown` on **any** runtime, exactly like an ordinary error, so finalizers run before the process exits with the recorded code.

## `CliColor`: one colour decision, shared by everything that renders

Both `effect/unstable/cli`'s own help/error rendering and anything your program renders itself should agree on whether output carries ANSI colour. `CliColor.enabled` is that decision, computed once per the [no-color.org](https://no-color.org) rule:

```ts with-api
import { CliColor } from "@effected/cli";
import { Effect, Stdio } from "effect";

Effect.runPromise(CliColor.enabled.pipe(Effect.provide(Stdio.layerTest({}))));
```

- Off when stdout is not a terminal.
- Off when `NO_COLOR` is set to any **non-empty** value — an empty `NO_COLOR=""` does not disable colour.
- `FORCE_COLOR` is **ignored**, matching core's own formatter.

The environment is read through the ambient `ConfigProvider`, never `process`, so a test swaps it with `Effect.provideService(ConfigProvider.ConfigProvider, ...)` rather than mutating `process.env`.

`CliColor.formatterLayer(overrides?)` builds `effect/unstable/cli`'s own `CliOutput.defaultFormatter({ colors })` from that same decision, so help text, parse errors and anything your program renders never disagree:

```ts
import { CliColor } from "@effected/cli";
import { NodeServices } from "@effect/platform-node";
import { Layer } from "effect";

// overrides replaces individual formatter methods without losing the rest —
// here, appending a "via <carrier>" line to the version output.
const Platform = CliColor.formatterLayer({
  formatVersion: (name, version) => `${name} v${version} (via mytool)`,
}).pipe(Layer.provideMerge(NodeServices.layer));
```

Each call mints a fresh layer; bind the result to a `const`, as above, or the decision is re-read every time it is provided.

## Rendering a multi-line failure

The `render` option of `reportFailures` may return an array, and each element becomes its own line. That is what turns a config failure into the shape a user can act on: the error's own message naming the file, then one indented line per rejected value.

```ts
import { CliRuntime, ConfigIssueRenderer } from "@effected/cli";
import { ConfigValidationError } from "@effected/config-file";
import { Effect } from "effect";

declare const program: Effect.Effect<void, ConfigValidationError>;

const main = program.pipe(
  CliRuntime.reportFailures({
    exitCode: 78,
    render: (error) =>
      error instanceof ConfigValidationError
        ? [String(error), ...ConfigIssueRenderer.render(error).map((line) => `  ${line}`)]
        : String(error),
  }),
);
```

```text
ConfigValidationError: Config validation failed at "/home/me/.config/app/config.toml"
  unknown key at variables.keep.KEEP_ME
  Missing key at variables.keep.file
  Missing key at variables.keep.value
```

### Telling a defect from a typed failure

`render` gets the squashed cause: the first typed failure when there is one, otherwise the first defect. Its second argument, `details`, says which one it is (`isDefect`) and carries the whole `cause`. So a typed failure can render as one line and a defect as a full report, and you don't have to guess from the error's shape:

```ts
import { CliRuntime } from "@effected/cli";
import { Cause } from "effect";

const main = program.pipe(
  CliRuntime.reportFailures({
    render: (error, { cause, isDefect }) =>
      isDefect ? ["Unexpected error, please report it:", Cause.pretty(cause)] : String(error),
  }),
);
```

A renderer that takes only `error` still works as before.

`ConfigIssueRenderer.render` takes the **error**, not its `issue`, because that is what an `Effect.catchTag("ConfigValidationError", …)` hands you and because `issue` is typed `Schema.Defect` — reaching into it at every call site is the ceremony this removes.

## The optional peer, and the rule that makes it honest

[`@effected/config-file`](/config-file) is a `peerDependenciesMeta.optional` peer, consumed only by `ConfigIssueRenderer`. The manifest declaration is the easy half. The load-bearing half is structural: **`ConfigIssueRenderer` is a module nothing else in the package imports**, with the shared rendering living in an internal module both renderers use and neither re-exports. An optional peer whose import is reachable from a shared module is not optional — it is a crash for every consumer who took the manifest at its word and did not install it.

The import is additionally `import type`, so it is erased at build time and the runtime reach is **zero**: a consumer without `@effected/config-file` installed can import this package, import that module, and call `render` on any value without the resolver ever being asked for the peer.

One consequence is worth stating rather than discovering. Because the type appears in a public signature, a consumer who has not installed the optional peer sees that one type fail to resolve — harmless at runtime, invisible under the common `skipLibCheck: true`, and real. It is the kit's established trade, the same one [`@effected/markdown`](/markdown) makes with its format peers: an optional peer buys install-time freedom and costs type resolution in the module that names it.

## Edge cases and failure modes

**`LogToStderr` is honoured in one direction only.** `References.LogToStderr` is core's own reference, and its own loggers respect it, so ignoring it here would make `CliLogger` surprising in a way nothing signals. Setting it forces *everything* to stderr — a consumer who sets it meant "this program's output is diagnostic". It can never move an error back onto stdout. That is the one guarantee this logger makes, and a reference should not be able to revoke it.

```ts with-api
import { CliLogger } from "@effected/cli";
import { Effect, References } from "effect";

const program = Effect.gen(function* () {
  yield* Effect.log("output line");
  yield* Effect.logError("diagnostic line");
}).pipe(Effect.provide(CliLogger.layer()), Effect.provideService(References.LogToStderr, true));

Effect.runPromise(program);
// stderr: output line
// stderr: diagnostic line
// stdout is empty — the override forces everything across, and never the reverse.
```

**An interrupt is left alone.** `reportFailures` passes an interrupt-only cause straight through without rendering anything: an interrupt is not a failure anyone wants printed, and the default teardown already maps an interrupt-only cause to `130`. A Ctrl-C therefore produces no error output at all.

```ts with-api
import { CliLogger, CliRuntime } from "@effected/cli";
import { Effect } from "effect";

const main = Effect.interrupt.pipe(CliRuntime.reportFailures(), Effect.provide(CliLogger.layer()));

Effect.runPromiseExit(main).then((exit) => console.log(exit._tag));
// Failure — and nothing was written to either stream.
```

**A renderer never throws.** Both renderers guard the value before reading it, so anything that is not an issue tree yields no lines. A rendering helper is called when something has *already* gone wrong, and it must never become the reason a program dies.

```ts with-api
import { SchemaIssueRenderer } from "@effected/cli";

console.log(SchemaIssueRenderer.render("not an issue tree"));
// []
```

That empty array is worth handling at the call site: print the error's own message alongside the rendered lines, as the multi-line `render` above does, so a value the renderer cannot describe still produces output rather than silence.

**Repeated lines are collapsed, deliberately.** A union reports every branch it tried, so one wrong key in a three-member union yields the same unknown-key line three times. The per-branch `Missing key` lines differ and are kept — they say which shapes *were* allowed — but the repetition in front of them is noise, so identical lines are deduplicated.

**Levels are filtered before the logger sees them.** `CliLogger` decides a *stream*, not whether a record is emitted at all; that is `References.MinimumLogLevel`, which defaults to `Info`. A `Effect.logDebug` line that never appears is being filtered upstream of this package, and the fix is to provide the reference — `Logger.withMinimumLogLevel` does not exist on the v4 line.

## Testing with @effect/vitest

The whole surface is testable **without stubbing a global**, which is the payoff of reading `Console.Console` off the fiber. Provide a capturing `Console`, run the program, and assert on what was written *and on which stream*.

The stream split is the property most worth pinning, because it is the one that silently regresses and the one `mytool run > log.txt` depends on. Test it at **both** thresholds: under the default `stderrFrom: "All"` every level goes to stderr, and under `stderrFrom: "Error"` — the split a tool whose output *is* its log lines reaches for — `Warn` is the discriminating boundary, since it must stay on stdout there and nowhere else.

```ts
import { CliLogger } from "@effected/cli";
import { assert, describe, it } from "@effect/vitest";
import { Console, Effect, References } from "effect";

const capturing = (): { readonly console: Console.Console; readonly out: string[]; readonly err: string[] } => {
  const out: string[] = [];
  const err: string[] = [];
  // Object.create(console) inherits the members nothing here touches, so the
  // double stays a Console without restating one.
  const double: Console.Console = Object.assign(Object.create(console) as Console.Console, {
    log: (...args: ReadonlyArray<unknown>) => out.push(args.map(String).join(" ")),
    error: (...args: ReadonlyArray<unknown>) => err.push(args.map(String).join(" ")),
  });
  return { console: double, out, err };
};

describe("CliLogger", () => {
  it.effect("routes every level to stderr under the default stderrFrom", () =>
    Effect.gen(function* () {
      const { console: double, out, err } = capturing();

      yield* Effect.gen(function* () {
        yield* Effect.logInfo("info");
        yield* Effect.logError("error");
      }).pipe(Effect.provide(CliLogger.layer()), Effect.provideService(Console.Console, double));

      assert.deepStrictEqual(out, []);
      assert.deepStrictEqual(err, ["info", "error"]);
    }));

  it.effect("routes every level at or above Error to stderr, and nothing below, with stderrFrom Error", () =>
    Effect.gen(function* () {
      const { console: double, out, err } = capturing();

      yield* Effect.gen(function* () {
        yield* Effect.logInfo("info");
        yield* Effect.logWarning("warn");
        yield* Effect.logError("error");
      }).pipe(
        Effect.provide(CliLogger.layer({ stderrFrom: "Error" })),
        Effect.provideService(Console.Console, double),
        Effect.provideService(References.MinimumLogLevel, "Debug"),
      );

      assert.deepStrictEqual(out, ["info", "warn"]);
      assert.deepStrictEqual(err, ["error"]);
    }));
});
```

Two habits keep such a suite honest. Drive levels with `References.MinimumLogLevel` provided as a service rather than reaching for a `withMinimumLogLevel` helper that does not exist. And when you assert the exit-code behaviour, write the test so that flipping the source value **fails** — assert that a marked error keeps its own code and that an unmarked one takes the fallback, rather than merely recording whatever the current implementation returns.

## Testing a built bin with `CliTest`

Everything above tests a program **in-process**, through a capturing `Console`. `@effected/cli/testing`'s `CliTest` is for the other case: proving a **built** bin — the actual artifact a user runs — behaves correctly, over a real subprocess.

```ts
import { CliTest } from "@effected/cli/testing";
import * as NodeServices from "@effect/platform-node/NodeServices";
import { assert, describe, it } from "@effect/vitest";
import { Effect } from "effect";

describe("mytool", () => {
  it.effect("exits 1 when it finds a problem", () =>
    Effect.gen(function* () {
      const sandbox = yield* CliTest.sandbox({ path: process.env.PATH ?? "" });
      const result = yield* CliTest.run("./dist/mytool.js", ["check"], {
        sandbox,
        execPath: process.execPath,
      });
      assert.strictEqual(result.exitCode, 1);
      assert.include(result.stdout, "2 problems found");
    }).pipe(Effect.scoped, Effect.provide(NodeServices.layer)),
  );
});
```

`CliTest.sandbox({ path })` mints a scoped temp directory with a fresh `HOME` and `XDG_{CONFIG,DATA,STATE,CACHE}_HOME`, `NO_COLOR: "1"`, and `path` as `PATH` — the host environment is never inherited. `CliTest.run(bin, args, { sandbox, execPath, cwd?, env?, stdin? })` spawns `execPath` with `[bin, ...args]` over core's `ChildProcess`/`ChildProcessSpawner` and returns `{ exitCode, stdout, stderr }` as **data** — a non-zero exit is never a failure, matching the findings pattern `CliExit` exists for.

**When `stdin` is omitted, or passed as `""`, the child receives an already-ended empty input, never an open pipe.** `effect/unstable/process`'s default `"pipe"` stdio stays open until something writes to and ends it, so a stdin-reading bin would otherwise hang the test.

A **reachability test** guards the split: nothing reachable from `@effected/cli`'s main entrypoint may import `CliTest`, with a positive control proving the import walker actually resolves modules — so importing the package for production use never pulls `effect/unstable/process`'s subprocess machinery into the bundle.
