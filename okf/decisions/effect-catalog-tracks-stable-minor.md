# The effect catalog takes caret ranges on the stable line

## Context

[The exact-pin decision](effect-catalog-exact-pins.md) held while Effect v4 was a run of release candidates. A caret on a prerelease floated across the release line, and a moving install could leave the vendored `.repos/effect` describing a surface that was not installed.

Effect 4.0.0 is the first stable v4 release.[^effect-4-release] Its release notes make three promises that change the trade:

- `effect` and every `@effect/*` package share one version and are released together.
- An API with no stability tag follows semver.
- An API tagged `@stability unstable` may break in a minor release.

## Decision

The `effect` and `effect:peers` catalogs, generated by [`pnpm-plugin-effect`](../modules/pnpm-plugin-effect.md), give `effect` and every `@effect/*` satellite the caret range `^4.0.0` under the `lock-minor` strategy. Every published `@effected/*` package advertises `^4.0.0` as its `effect` peer. `@effect/tsgo` versions on its own line and keeps its own range.

The exact `effect` the kit builds and tests against is the lockfile's resolution. `.repos/effect` is pinned to the tag matching that resolution, and is re-pinned whenever the lockfile's `effect` moves, not only when the catalog literal does.

## Alternatives rejected

- **Keep exact pins under `lock`.**
  - Every Effect patch would become a kit-wide release.
  - Every consumer would be forced onto the one patch the kit last advanced to, even though a stable patch is semver-compatible by Effect's own promise.
  - The vendored-source drift that justified exact pins is now handled by pinning `.repos/effect` to the lockfile's resolution.
- **A tilde range (`~4.0.0`).** It would keep consumers off a new Effect minor until the kit advanced. That is the narrower guard against the `@stability unstable` APIs the kit builds on (see Consequences), but it rejects every compatible minor and makes each Effect minor a kit-wide release again. The owner chose the caret.

## Consequences

- **Advances follow the lockfile.** One wave per moving lockfile, not one per catalog edit.
  - The orientation hook's `EFFECT_PIN` and the bats `EXPECTED_PIN` move with the lockfile, as does the re-pin of `.repos/effect`.
  - So do the skill line anchors in `plugins/claude-code/__test__/helpers/skill-anchors.json`.
  - Procedure: [advance the effect pin](../runbooks/advance-the-effect-pin.md).
- **An Effect minor can break the kit.** Much of what the kit imports is tagged `@stability unstable` at 4.0.0: most of `cli`, all of `process`, `rpc` and `sql`, and much of `ai` and `http`. A consumer can resolve a newer Effect minor than the kit was tested against, and an unstable API can change shape in it.
  - The kit's own CI catches this only when its lockfile moves.
  - Until then, the guard is the advance itself: move the lockfile, rebuild, retest, release.
- **One resolved copy still matters.** Two copies of `effect` are still two sets of service tags. A caret range makes duplicates rarer between kit releases, but a release candidate still in the toolchain is a separate copy by design. See [one resolved effect copy](../conventions/one-resolved-effect-copy.md).

[^effect-4-release]: The `effect@4.0.0` release notes, "Packaging and versioning".
